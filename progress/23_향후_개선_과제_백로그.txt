   np.diff+np.where+np.concatenate로 [시작거리, 끝거리, 대표경사각]

   직접 작성 예정): 위 배열로 세그먼트 진입 전 목표속도 상한 계산.

   sqrt(v_exit_cap² - 2·a_coast·L). mpc_speed()의 speed_limit 클립
   자리에 v=min(v, downhill_v_cap) 추가.

   가속 해제, 내리막(a_coast<=0)은 신규 상수 simpara.decel_active
   (회생제동 배제, 기계 브레이크 감속도)로 같은 공식. 코스팅/제동
   중엔 P_batt=power.P_LV_race만(배터리 안 거침).

[ 2순위 - 예전부터 보류 중이던 항목 ]
1. 속도값 정수(int) 출력 반영 - 결정만 되고 아직 미반영. 내부
   물리 계산(dt, P_batt, update_soc 등)과 EMA/tanh 댐퍼는 계속
   float로 정밀하게 유지, 정수 반올림은 **결과 저장/출력 시점에만**
   (run_simulation()의 results.append({"v": ...}) 부분) 적용.
   매 스텝 내부 계산까지 정수로 강제하면 댐퍼가 계산한 1km/h 미만
   조정분이 반올림으로 0이 되어 속도가 고착되는 문제가 있어 제외.
2. Optuna 트라이얼 병렬화(SQLite WAL 모드 + 별도 프로세스) - 탐색
   재실행 직전 처리하기로 계속 보류 중. n_jobs는 GIL 때문에
   CPU-bound 순수 Python 루프엔 실효성 없음, 별도 프로세스 여러
   개(4코어 확인됨)를 같은 SQLite storage에 붙이는 방식 필요,
   sqlite3.connect(...).execute("PRAGMA journal_mode=WAL;") 권장.
   Colab은 이 워크로드(상태 의존적 순차 Python 루프)엔 안 맞아서
   검토 안 하기로 함.
3. momentum_gain을 Optuna 탐색공간에 넣을지 여부 - 위 1~5 정리
   끝나고 본 탐색 재실행할 때 같이 결정.
4. (선택, 급하지 않음) mpc_speed()의 np.clip() 스칼라 호출을 순수
   파이썬 max()/min()으로 교체.

[ 참고 - 실제 MPC 정의 대비 현재 모델의 한계 (분석, 액션 아이템 아님) ]
없는 것: 명시적 예측 모델 기반 수치 최적화(매 스텝 비용함수를
최소화하는 제어 시퀀스를 실제로 풂), 명시적 objective function,
제약조건을 최적화 내부에서 다루는 것(현재는 soc_cutoff/v_max/
speed_limit 등 전부 사후 클리핑).
있는 것: receding horizon(매 스텝 상태 재측정 후 재계산), 상태
피드백, 부분적 예측(avg_gen_ratio, slope_ahead).
전환 순서 합의: 위 1순위(코스팅/제동/세그먼트) 규칙 기반으로 먼저
완성 -> 물리적으로 말이 되는지 검증 -> 그 다음 비용함수+solver로
재구성. 오르막은 배터리 I²R 손실(제곱 손실) 기반 비용항으로,
energy_crit의 균등배분 가정도 지형 기반 1회성 예산 배분으로 재설계
예정(둘 다 설계 논의만 완료, progress/22 참고).
