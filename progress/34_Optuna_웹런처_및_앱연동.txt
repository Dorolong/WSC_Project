[ 배경 ]
Streamlit Cloud 무료 티어로는 Optuna 탐색(수십 trial, 각 trial이 K=5개
날씨 시뮬레이션)을 돌릴 수 없다고 progress/24에서 이미 결론이 나 있었음.
그렇다고 로컬 노트북을 켜둔 채로만 돌릴 수 있으면 팀원이 각자 탐색을
해볼 수가 없음. -> 오라클 클라우드 무료 인스턴스에 별도의 FastAPI 런처를
띄워서, 팀원들이 웹에서 로그인 후 각자 독립된 Optuna 탐색을 큐에 넣고
진행률을 지켜볼 수 있게 만듦.

[ 아키텍처 - 앱이 2개로 분리됨 ]
1. Streamlit 앱 (Streamlit Cloud 배포, 기존 app.py)
   - 단일 시뮬레이션 실행 + 결과 시각화 + 차량 제원 설정 담당
   - 무거운 탐색은 안 함
2. Optuna 웹 런처 (오라클 서버, 신규 server/ 폴더)
   - server/main.py (FastAPI): 인증/큐/상태 API + 정적 프론트 서빙
   - server/study_runner.py: 실제 탐색을 도는 별도 프로세스
   - server/static/index.html: 로그인·실행·진행률 UI (순수 HTML/JS)
   - server/wsc-launcher.service: systemd 유닛(재부팅 자동 기동)
   - server/README.md: 배포 가이드(scp/clone -> venv -> systemd)
두 앱은 **같은 Supabase 프로젝트를 공유**해서 계정/결과가 이어짐.
Streamlit 앱 사이드바의 "Optuna 탐색 서버로 이동" 버튼(app.py의
WSC_OPTUNA_SERVER_URL = http://141.147.167.152:8000)으로 연결됨.

[ server/main.py 설계 요점 ]
- 인증: 프론트가 Supabase에서 받은 access token을 Authorization 헤더로
  보내면, 서버가 Supabase /auth/v1/user에 물어봐서 검증(verify_user).
  자체 사용자 DB를 만들지 않고 기존 Supabase Auth를 그대로 재사용.
- 동시 실행 제한: WSC_MAX_CONCURRENT(기본 1, 서버 사양이 작아 보수적)
  만큼만 동시에 돌리고 나머지는 QUEUE에 대기. 2초마다 도는 watcher
  스레드가 끝난 프로세스를 정리하고 다음 대기자를 시작시킴.
- 남용 방지: WSC_MAX_TRIALS(기본 100) 초과 요청 거부.
- 진행률: study sqlite를 직접 세지 않고, study_runner가 매 trial마다
  갱신하는 가벼운 progress.json을 읽음(로테이션돼도 경로가 안 바뀜).
- 대기 예상시간: 실제 관측된 "trial당 소요시간"(_last_known_pace_seconds)
  을 실행이 진행될수록 실측값으로 갱신해서 대기열 예상시간에 반영.
- /api/my-active-run: 브라우저를 새로고침해도 "내가 뭘 돌리고 있었는지"
  다시 찾아서 진행 카드를 이어 보여주기 위한 엔드포인트.

[ server/study_runner.py 설계 요점 ]
- FastAPI 프로세스 안에서 study.optimize()를 돌리면 블로킹돼서 다른
  요청까지 막히고, GIL 때문에 스레드로도 진짜 병렬이 안 됨 ->
  subprocess로 OS 프로세스를 분리 (백로그에 있던 "Optuna 병렬화는
  별도 프로세스로" 결론과 같은 이유).
- 탐색 공간/시뮬레이션 셋업은 scripts/main.py의 build_objective()를
  import해서 재사용 - 웹과 CLI가 같은 코드를 쓰도록 해서 파라미터
  범위가 두 군데로 갈라지는 걸 방지.
- CHECKPOINT_EVERY(기본 20) trial마다 Supabase optuna_runs 테이블에
  현재 최적값을 upsert -> 서버가 죽어도 결과는 계정에 남음.
- **디스크 로테이션**: 체크포인트마다 여유 공간을 확인해서
  MIN_FREE_BYTES(500MB) 밑으로 떨어지면 지금까지의 study sqlite를 지우고,
  best_params를 enqueue_trial로 미리 넣어둔 새 study로 이어감. 무료
  인스턴스의 작은 디스크에서도 긴 탐색이 죽지 않게 하는 장치.
- sqlite는 만들기 전에 PRAGMA journal_mode=WAL로 열어둠(진행 중에도
  다른 프로세스가 읽을 수 있게).

[ scripts/main.py 재구성 ]
기존 스크립트 본문을 세 함수로 분리:
- build_objective() -> (objective, context): 데이터 로딩·날씨 K개 생성·
  탐색공간 정의까지. context에 cfg/route_np/dist_vals 등 후처리에 필요한
  값들을 담아 반환.
- run_best_params_simulation(best_params, context, output_csv): 탐색 후
  최적값으로 한 번 더 시뮬레이션.
- run_cli(): 기존 `python scripts/main.py` 진입점.
또한 **내리막 세그먼트 경계 배열 추출(백로그 1순위 1번)이 완성됨**
(main.py 112~130줄) - np.diff/np.where로 is_downhill 경계를 찾아
[시작거리, 끝거리, 대표경사각] 배열 생성. 단, 이걸 쓰는
compute_downhill_cap()이 아직 없어서 지금은 계산만 하고 미사용.

[ Streamlit 앱(app.py) 쪽 변경 ]
- **simpara 세션 격리(v1.0.8)**: build_default_cfg()에 simpara 추가,
  run_simulation()도 cfg.simpara를 쓰도록 변경. "차량 제원 설정"에
  "시뮬레이션 설정" 탭 신설(신호등/보행자 대기시간, soc_hard_stop,
  max_v_delta, decel_brake). 예전 physics/race와 같은 종류의 전역상태
  누수 버그를 simpara에 대해서도 해소. **단 mpc_controller.py는 아직
  전역 simpara를 참조 - 아래 "알려진 버그" 참고.**
- **자동 로그인**: 신규 components/session_storage/ JS 컴포넌트로
  Supabase refresh token을 브라우저 localStorage에 저장해두고, 페이지를
  새로 열 때 refresh_session()으로 세션 복구 시도. 로그아웃 시 clear.
- **내 Optuna 탐색 결과**: 사이드바에서 optuna_runs 테이블을 조회해
  진행률·최적값을 보여주고, "이 파라미터로 시뮬레이션하기"를 누르면
  st.session_state.active_best_params로 세션 동안 적용(사이드바 MPC
  파라미터 표 헤더도 "(내 Optuna 탐색 결과 적용됨)"으로 바뀜,
  "기본값으로 되돌리기" 버튼 있음).
- **코드 보기**: GitHub raw에서 주요 파일을 그때그때 받아와서 읽기
  전용으로 보여주는 다이얼로그(st.cache_data ttl=30).
- 릴리즈 노트 v1.0.7(탐색 서버 연동), v1.0.8(시뮬레이션 설정 탭) 추가.

[ Supabase 스키마 추가분 (optuna_runs) ]
study_name(고유, on_conflict 대상), user_id, n_trials_completed,
n_trials_target, best_value, best_params(jsonb), status(running/done/
error), termination_reason, updated_at. RLS는 기존 테이블들과 같은
방식(본인 행만)일 것으로 보이나, **SQL 원문이 레포에 남아있지 않음** -
SETUP.md에도 미기재. 다음에 Supabase를 새로 세팅할 일이 생기면 이
테이블 정의를 다시 만들어야 하므로 백로그에 등록.
