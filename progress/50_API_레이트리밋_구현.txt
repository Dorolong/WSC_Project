API 레이트 리밋 구현 (2026-08-05)
================================================================

[ 배경 ]
docs/codex_security_tasks.txt 의 작업 1. HTTPS 배포 후 공개 도메인에
스캐너 probe 가 실제로 잡혔고, /api/* 폴링과 실행 생성 요청에 제한이 없었다.
회원가입 모달과 서버 재시작 상태 복원은 사용자가 이미 해결했다고 확인했다.

[ 설계 ]
1. /api/* 전체는 접속자 IP 기준 sliding window 로 제한.
   - 기본값: WSC_RATELIMIT_API_PER_MIN=300
   - 정상 사용자가 시뮬레이션 중 분당 약 75건을 보내므로 4배 여유.
2. POST /api/runs, POST /api/sim/runs 는 user_id 기준 sliding window 로 제한.
   - 기본값: WSC_RATELIMIT_RUN_PER_HOUR=20
   - 같은 NAT 뒤 팀원들이 서로를 막지 않게 IP 가 아니라 인증 후 user_id 사용.
3. WSC_RATELIMIT_ENABLED=0 킬 스위치를 둔다.
4. 정적 파일은 제외하고 /api/* 만 제한한다.
5. 429 응답에는 Retry-After 헤더와 한국어 detail 을 포함한다.

[ 구현 ]
- server/rate_limit.py 신설.
  - SlidingWindowLimiter: deque 기반 sliding window.
  - ApiRateLimitMiddleware: /api/* IP 기준 제한.
  - enforce_run_creation_rate(): 실행 생성 API user_id 기준 제한.
  - uvicorn 단일 worker 전제를 코드 주석에 기록. workers>1 로 늘리면
    Redis 같은 공유 저장소가 필요함.
- server/main.py
  - ApiRateLimitMiddleware 등록.
  - create_run(), create_sim_run() 에서 verify_user() 이후
    enforce_run_creation_rate(user.id, path) 호출.
  - 429 도 기존 log_requests 미들웨어를 지나도록 미들웨어 등록 순서를 배치.
- server/README.md, server/wsc-launcher.service
  - WSC_RATELIMIT_* 환경변수와 킬 스위치 문서화.
  - 이미 구현된 RUNS_STATE_PATH 상태 복원 설명도 현재 코드에 맞게 정정.
- app.py, server/static/data/release-notes.json
  - v1.1.2 릴리즈 노트 추가.
- README.md
  - 다음 할 일을 docs/codex_security_tasks.txt 기준으로 갱신.

[ 지시서와 다르게 판단한 부분 ]
실행 생성 요청 제한은 "미들웨어만"으로는 user_id 기준 키를 알 수 없다.
미들웨어에서 Supabase verify 를 다시 호출하면 인증 외부 호출이 2배가 되므로,
공통 limiter 는 server/rate_limit.py 에 두되 라우트 함수에서 verify_user()
이후 helper 를 호출하는 방식으로 구현했다.
