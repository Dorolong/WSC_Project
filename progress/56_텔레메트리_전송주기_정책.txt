================================================================
[결정] 텔레메트리 전송 주기 정책 + SD카드 용량 산정
================================================================
결정일: 2026-08-06

[ 배경 ]
Phase 2(실시간 수신) 설계에 저장 용량 추정이 필요한데, specs 엑셀에
CAN 신호별 전송 주기가 **한 건도 기재돼 있지 않았다**(108개 전부).
워크북 전체를 검색해 확인했고, 헤더에도 주기 컬럼이 없다.
사용자가 임의 설정하기로 하고 아래와 같이 결정했다.

[ 결정 - 2단 정책 ]
10Hz(100ms) 12개:
  BMS PRIMARY 10개  0x040~0x047(HV BOT/TOP), 0x6F4, 0x6FA(LV)
  모터 2개          0x402(Bus_Voltage/Current), 0x403(Motor_Velocity)
1Hz(1000ms) 나머지 96개

근거:
- 태양광차는 포뮬러급 과도현상이 없어 상시 고속 샘플링이 불필요하다
  (사용자 판단). 언더샘플링으로 없던 피크가 생기는 것(에일리어싱)이
  오히려 위험하므로 필요한 신호만 올린다.
- 0x402/0x403 을 10Hz 로 올린 이유 두 가지:
  (a) 0x403 은 **시간 미분해서 가속도를 얻는다**(가속도 CAN 신호가
      아예 없다 - 엑셀 "시뮬레이션 연계" 시트). 1Hz 를 미분하면
      F_acc 항이 매우 거칠어진다.
  (b) **I²R 손실은 전류의 제곱이라 평균 전류로 계산하면 과소평가된다**
      (mean(I²) > mean(I)²). progress/22 의 비용함수 MPC 전환에서
      오르막 비용을 I²R 기반으로 설계하기로 했으므로 전류 해상도가
      그 계수 실측에 직접 들어간다. BMS 10Hz 판단의 근거이기도 하다.
  비용은 SD 1.0GB -> 1.1GB 로 사실상 없다.
- 반대 방향 근거도 기록해둔다: 누적 카운터(Odometer, 소모 Ah)는
  **차분하면 샘플링 주기와 무관하게 정확**하다. 에너지 총량만 볼 거면
  1Hz 로 충분하고, 주기가 필요한 건 순간값의 분산을 보는 경우다.

[ 산정 결과 (telemetry.signals.expected_frame_rate() 로 계산) ]
  SD 기록   216 frame/s  -> 대회 전체(72h) 바이너리 약 1.1 GB
  서버 수신 174 frame/s  -> 대회 전체 원본 약 9.0 GB (SD_ONLY 42개 제외)

  SD카드 권장: **32GB 이상, 고내구(High Endurance)/산업용 등급**
   - 용량은 32GB 로 충분(대회 전체 1.1GB, 30배 여유). 64GB 면 넉넉.
   - **용량보다 온도가 위험 요소다.** 호주 아웃백 주행 중 차량 내부는
     60~70도까지 오른다. 소비자용 카드는 고온에서 쓰기 오류·수명 저하가
     심해 시험 주행 하루가 통째로 날아갈 수 있다.
   - 쓰기 수명(TBW)은 걱정 없음(대회 전체가 몇 GB). 속도 등급도 무관
     (216 frame/s x 20B = 초당 약 4KB).
   - **저장 형식이 5.3배를 가른다**: canlog.csv 실측 프레임당 106B(텍스트)
     vs 바이너리 20B. 바이너리로 남기고 분석 시 변환할 것.

[ 서버 저장은 별개 문제로 남는다 ]
주기를 낮춰도 서버 원본은 9GB 로 Supabase 무료(500MB)는 물론 Pro(8GB)도
넘는다. **집계 저장으로만 풀린다.** 엑셀 "테스트 후 상관분석" 시트에
이미 방향이 있다: "시험 전에는 모든 CAN 신호를 저장한다"(선별 전) +
"100ms 또는 1s 단위로 정리한다"(분석 해상도).
-> Phase 2 설계: 실시간 표시는 최근 구간만, 분석용은 1Hz 집계,
   원본은 코스트다운 시험 같은 한정 구간만 요청 시 저장.
   참고: 12개 신호 100Hz x 5분 = 36만 프레임 = 72MB (시험 구간은 저렴)

[ 구현 ]
- specs/can_signal_rates.csv 신설(108행). can_id, group, priority, name,
  tx_period_ms, source, note.
  **can_signals.csv 에 넣지 않은 이유**: scripts/can_signals_from_xlsx.py
  가 엑셀에서 그 파일을 통째로 덮어쓰기 때문에 주기 컬럼이 재생성 때
  사라진다. 또 주기는 엑셀의 하드웨어 사실이 아니라 우리가 정한 설정
  정책이라 출처를 분리하는 편이 맞다.
- telemetry/signals.py:
  - load_rate_policy() 추가, load_signal_defs() 가 tx_period_ms 를 병합.
    주기 파일이 없으면 기본 1000ms.
  - expected_frame_rate(include_sd_only) 추가. 용량 산정과 배치 주기
    결정에 쓴다. 숫자를 문서에 박지 않고 코드에서 뽑게 했다.

[ 남은 확인사항 ]
1. 이 주기는 **임의 설정값**이다. WaveSculptor22 매뉴얼과 BMS/MPPT
   설정에 실제 전송 주기가 있으므로, 확인되면 source 를 "실측"으로
   바꾸고 값을 갱신할 것. 결론(SD 32GB)은 바뀌지 않는다 - CAN 버스
   물리 상한이 500kbps 기준 약 3,900 frame/s 라 최악도 20GB 다.
2. **MPPT #2·#3 의 14개는 우선순위가 비어 있다.** 엑셀에 "#1과 동일
   오프셋 구조"로만 적혀 있어 변환 때 못 채웠다. #1과 같게 채우면
   될 것으로 보이나 확인 필요.
3. 엑셀에 tx_period_ms 컬럼을 추가하면 이 파일과 이중 관리가 되므로,
   추가한다면 변환 스크립트가 그것을 읽도록 같이 고칠 것.
