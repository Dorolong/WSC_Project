[방향 재정립] 계층별 로드맵 - 인계물 중심으로 재편
================================================================
결정일: 2026-08-06

[ 왜 다시 짰나 ]
사용자가 두 가지를 밝히면서 기존 계획의 전제가 바뀌었다.
 (1) **호주에 가지 않는다.** 만든 모델만 보내 팀원 노트북에 탑재한다.
 (2) 현장 표시는 feature/ocs 의 ArrowPoint 대시보드를 쓴다.
 (3) 발표용 산출물은 필요 없다.
-> 인계물이 "돌아가는 시스템"이 아니라 **모델**이 됐다. 여기에 맞춰
   무엇을 만들고 무엇을 안 만들지 전부 다시 정렬했다.

[ 계층 구조 - 아래가 위를 떠받친다 ]
  L0 인계물    권장속도 표(가치함수)          <- 호주로 나가는 유일한 것
  L1 결정      DP 최적화 (거리 x SOC x 온도 x 시간여유)
  L2 예측      주행저항·SOC·발전 + **열** + 잔차 보정
  L3 데이터    시험 주행 텔레메트리 (Phase 1, 보정용)
  L4 인프라    시뮬레이터·Optuna 서버·업로드   <- 전부 한국에 남음

[ 무엇이 바뀌었나 ]
  인계물        시스템 -> **표 파일 하나**
  Phase 2       다음 작업 -> **취소**(팀원 ArrowPoint 가 이미 수신)
  대시보드      우리가 제작 -> **제작 안 함**(현장 것 사용)
  텔레메트리    실시간 표시 -> **모델 보정용 데이터 공급**
  열·온도       없음 -> **L2 에 신규 추가**
  AI 역할       속도 판단 -> **예측·잔차 보정**
  웹·서버       최종 산출물 -> **개발 도구(L4)로 격하**

[ L0 인계물 - 왜 표인가 ]
현장에 만든 사람이 없다. 그러면 **고장날 여지가 가장 적은 형태**가
최우선 기준이 된다.
 - DP 로 풀면 결과물이 애초에 표다(거리 x SOC x ... -> 속도).
 - 파이썬 실행환경도, 죽을 프로세스도 없다. 파일 읽기가 전부다.
 - Java 대시보드가 몇 줄로 읽는다. 값을 눈으로 확인할 수도 있다.
**"DP 로 간다"는 결정이 인계 형태까지 자동으로 해결한다.**
표는 정적 스케줄이 아니라 **정책**이다 - 축이 상태이므로 날씨가
계획보다 나쁘면 SOC 가 낮아지고 표가 다른 속도를 내놓는다.

[ L1 결정 계층 ]
 - 규칙 기반 LV1~LV8 을 비용함수로 재구성. 대부분의 보정항이 사라지고
   물리 모델 안으로 흡수된다(progress/22 참고).
 - solver 대신 DP: 상태가 적어 전역 최적이 보장되고, numpy 만 있으면
   되고, 결과가 곧 인계물이다.
 - 상태 축: 거리 x SOC x 온도 x 시간여유.
   **"시간여유" 정의는 미확정** - 남은시간/다음CS마감까지/일정편차 중
   무엇으로 할지 정해야 한다. 설계의 관건.
 - 격자 예: 거리 600 x SOC 100 x 온도 40 = 240만 칸. 노트북에서 수 초.

[ L2 예측 계층 - 열이 신규 ]
현재 물리엔진에 **온도 항이 아예 없다**(엑셀 "시뮬레이션 연계" 시트에도
"열 디레이팅 - 현재 미모델링"으로 기재).
 - 1차 집중열용량 모델: dT/dt = (P_loss - hA(T - T_ambient)) / mc
   발열 P_loss 는 이미 아는 I2R, 미지수는 mc 와 hA **두 개뿐**이다.
 - **회색상자 권장**: 물리 구조를 주고 계수만 데이터로 피팅. 신경망은
   이 방정식을 데이터로 다시 발견해야 해서 데이터가 훨씬 많이 든다.
 - 디레이팅 임계는 WaveSculptor22 매뉴얼 + 실측 확인.
 - **AI(학습)의 자리는 잔차**다: 냉각 유동, 태양 복사 가열, 부품 간
   열결합처럼 1차 모델이 못 잡는 부분. 입력이 이미 좋아서(속도·전류·
   외기·일사) 작은 모델로 충분하다.
 - 열은 **느린 상태**다(시정수 분 단위). 초 단위 반응이 필요 없어
   상태 하나 추가의 부담이 작다.
 - **progress/22 의 "오르막 I2R 비용"과 같은 문제다.** 오르막 -> 전류
   증가 -> 손실 제곱 증가 -> 온도 상승 -> 디레이팅. 별개 기능이 아니라
   그 설계의 완성이다. 지금 slope_k 로 눌러둔 부분에 물리 근거가 생긴다.

 [즉시 필요한 수정] scripts/main.py:52 의 ENV_NEEDED_COLS 가 메모리
 절약을 위해 temperature_2m 을 버리고 있다. 열 모델을 넣으려면
 되살려야 한다(env_data.csv 에는 이미 들어있다).

[ L3 데이터 계층 - Phase 1 은 살아있다 ]
실시간 수신은 취소지만 **데이터 경로는 계속 필요하다.**
Regen_eff=0.6, Cd=0.081, motor_eff=0.97 등이 아직 카탈로그·이론값이고,
시험 주행 로그를 업로드해야 실측으로 교체된다.
 -> 이미 완성된 Phase 1(업로드·파싱·저장·차트)이 그 역할을 한다.
 -> 열 모델 계수(mc, hA) 피팅도 이 데이터로 한다.

[ L4 인프라 - 격하되지만 버려지지 않는다 ]

[추가 2026-08-06] 표 구조 확정 + 비용함수 설계
================================================================

[ "시간 여유" 축 - 셋이 아니라 하나였다 ]
앞서 미확정으로 남겼던 세 후보(남은시간 / 다음CS마감까지 / 일정편차)는
**전부 (거리, 시각)에서 파생된다**:
  남은 시간      = 27일 마감 - 현재 시각
  다음 CS 마감까지 = (거리로 다음 CS 결정) 그 마감 - 현재 시각
  일정 대비 편차   = 현재 시각 - 계획 시각(거리)
-> 축을 셋 늘릴 필요 없이 **시각 하나면 된다.**

[ 차원의 저주 - 한 표에 다 넣으면 터진다 ]
속도를 uint8(1바이트)로 저장한다고 가정한 크기:
  거리600 x SOC100                              0.1 MB
  + 시각200                                    12   MB
  + 모터온도30                                 360   MB
  + 배터리온도30 (사용자 요청: 열 둘 다)        10.8 GB   <- 불가

[ 해법 - 큰 표 하나 대신 작은 표 셋 (확정) ]
  A. λ 표      거리600 x SOC100 x 시각편차100      6.0 MB   "에너지가 얼마나 귀한가"(전략)
  B. 속도 표    λ50 x 경사40 x 정면풍20            0.04 MB  "그 가격에 이 지형이면 얼마"(전술)
  C. 열 상한    모터온도60 x 배터리온도60          0.004 MB "열 때문에 못 넘는 선"(제약)
  합계 약 6 MB  (10.8GB 대비 1800배 축소)

현장 조회는 세 줄:
    λ    = A[거리, SOC, 시각편차]
    v    = B[λ, 경사, 정면풍]
    권장 = min(v, C[모터온도, 배터리온도])

가능한 이유: **온도는 속도를 "결정"하지 않고 "제한"한다.** 그래서 곱하지
않고 마지막에 자르면 된다. λ가 전략을 요약해주니 지형도 분리된다.
부수효과로 **각 조각을 따로 검증할 수 있다** - 거대한 표 하나는 틀려도
어디가 틀렸는지 모른다.

[ 파일 형식 (확정) ]
 - B, C 표 -> **CSV**. 작고, 눈으로 확인 가능하고, Java 가 몇 줄로 읽는다.
 - A 표    -> **바이너리**. 헤더(축 범위·격자 수) + uint8 배열.
              Java RandomAccessFile 로 바로 인덱싱. CSV 로 하면 600만 행
              = 약 100MB 라 부담.
 - Parquet 은 Java 쪽 라이브러리가 필요해 채택 안 함.
   **현장에서는 의존성이 없는 게 최고다.**

[ 비용함수 - 거리 매개변수화 ]
상태 x = (t, SOC, T_m, T_b), 제어 v, 독립변수 s(거리)
    dt   = ds/v
    dSOC = -(P_batt(v, θ, wind, irr) / E_pack) dt
    dT   = ((P_loss - hA(T - T_amb)) / mc) dt

표준형:  J = Σ L(x_k, u_k) + V_f(x_N)

 [A] 시간 최소화 + 에너지 제약  <- **권장 시작점**
     min Σ ds_i/v_i
     s.t. SOC >= SOC_min, t(CS_k) <= 마감_k, v <= v_cap
     튜닝 파라미터가 사실상 없다. 물리가 다 한다.
     에너지 제약을 라그랑주로 완화하면 그 승수가 **λ** 이고 구간별로 분리:
         v* = argmin_v (1 + λ·P_batt(v)) / v

 [B] 소프트 제약
     J = Σ [ ds/v + ρ_soc·max(0, SOC_min - SOC)² + ρ_t·max(0, t - 마감)² ]
     하드 제약은 DP 격자에 **해가 없는 칸**을 만든다. 소프트면 "얼마나
     위반했는지"가 보여 디버깅이 쉽다. **개발 초기엔 B, 확정되면 A.**

 [C] 부드러움
     J = Σ [ ds/v + w_Δ (v_i - v_{i-1})² ]
     지금 EMA+tanh 댐퍼가 하던 일을 원리적으로 대체.

 [D] 열을 비용으로
     J = Σ [ ds/v + w_T·max(0, T - T_warn)² ]
     하드 상한은 무디다. 소프트면 잠깐 넘는 것과 계속 높은 것을 구분.

 **원칙**: 항을 추가할 때마다 가중치가 생기고 그 가중치가 다시 튜닝
 대상이 된다. 파라미터 12개를 없애려고 가는 건데 가중치를 잔뜩 붙이면
 이름만 바뀌고 제자리다. **A 로 시작해 정말 필요할 때만 추가할 것.**

[ 룰베이스 처분표 ]

   └ radi_risk        **유지** 예보 불확실성 할인. 보수적 예측치로 DP 를 도는 방식
