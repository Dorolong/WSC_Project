(2026-07-13) 경로 지도 애니메이션 - 커스텀 컴포넌트 디버깅 과정
================================================================

[ 목표 ]
시뮬레이션 실행 중/후에 Darwin~Adelaide 경로를 시각적으로 보여주기
(README TODO에 있던 항목). "호주를 가로지르는" 진행 상황을 부드럽게
보여주고 싶다는 요청.

[ 시도 1: Plotly Scattermapbox 반복 갱신 ]
progress_cb 콜백 안에서 st.empty() placeholder에 st.plotly_chart()를
반복 호출하는 방식. 문제: 매 호출마다 지도 타일(OpenStreetMap)이 통째로
다시 로드되면서 심하게 깜빡임. key를 매번 다르게/같게 둘 다 시도했으나
(같은 key는 StreamlitDuplicateElementKey 에러) 근본 해결 안 됨.

[ 시도 2: Scattermapbox -> 좌표 기반 Scatter ]
지도 타일 자체를 없애면 깜빡임이 없어질 거라 판단, 위경도를 그냥 x/y
좌표로 쓰는 일반 Scatter 플롯으로 전환. 타일 로딩은 없앴지만 여전히
깜빡임 지속 -> 원인이 "타일 재로딩"이 아니라 "st.plotly_chart를 한 실행
안에서 반복 호출할 때마다 Streamlit이 컴포넌트를 매번 새로 마운트하는 것"
자체였음을 확인.

[ 시도 3: 커스텀 Streamlit 컴포넌트 (components/route_animator/) ]
Node.js 설치 없이 순수 HTML/JS로 구현 (declare_component(path=...)로
정적 파일 서빙, React/webpack 빌드 불필요).

버그 A - 외부 CDN 의존:
  처음에 https://cdn.jsdelivr.net/npm/streamlit-component-lib@2.0.0/dist/
  streamlit-component-lib.js를 <script> 태그로 로드하려 했으나 실제로는
  그 경로에 UMD 번들이 없음(해당 패키지는 ES 모듈 기반이라 CDN
  스크립트 태그용 번들 제공 안 함). 결과: `Streamlit is not defined`
  콘솔 에러, 컴포넌트 전체가 조용히 실패.
  -> 해결: window.postMessage 기반 프로토콜을 직접 구현해서 외부
     라이브러리 의존 자체를 제거.

버그 B - 반복 호출 시 iframe 재생성:
  progress_cb 콜백 안에서 커스텀 컴포넌트를 반복 호출했더니, 매번
  화면이 "떴다 사라지길" 반복. 커스텀 컴포넌트도 plotly_chart와 같은
  근본 한계(한 스크립트 실행 안에서 반복 호출하면 매번 새 iframe 마운트,
  key를 같게 하면 DuplicateWidgetID 에러)를 그대로 가짐을 확인.
  -> 설계 변경: 컴포넌트를 실행당 딱 2번만 호출하는 구조로 전환
     (시작 시 1회 + 계산 완료 시 1회). 실시간 progress 동기화는 포기하고,
     대신 브라우저 안에서 자체적으로 반복 재생되는 장식용 애니메이션 +
     별도의 st.markdown 텍스트로 실제 진행률 표시(텍스트는 반복 갱신해도
     문제없음을 이미 확인한 요소)로 역할 분리.

버그 C - isStreamlitMessage 플래그 오판:
  postMessage 프로토콜을 직접 구현하면서, 수신 메시지에도
  `isStreamlitMessage: true`가 붙어있을 거라 가정하고 그걸로 필터링함.
  실제로는 이 플래그는 컴포넌트->호스트 방향(송신)에만 붙는 것이고,
  호스트->컴포넌트 방향(수신, streamlit:render)에는 안 붙음.
  결과: 정상적으로 도착한 render 메시지를 전부 무시하고 있었음
  (겉보기엔 "아무것도 안 뜸"으로만 보여서 원인 특정이 어려�웠음).
  화면에 디버그 텍스트를 직접 찍어서(수신된 메시지 raw 내용 표시)
  원인 확정. WebFetch로 streamlit-component-lib 공식 소스(streamlit.js)
  직접 확인 후 수정: 수신 시엔 data.type만 체크하도록 변경.

버그 D - 마커 좌표 어긋남:
  현재 위치 마커를 SVG 밖의 별도 <div>로 만들어서 wrap.clientWidth/height
  기준으로 독립적으로 스케일링했는데, SVG는 viewBox+preserveAspectRatio로
  종횡비를 유지하며 그려지다 보니(레터박싱 발생) 실제 SVG 렌더링 위치와
  <div> 마커의 계산 위치가 어긋나서 마커가 경로 밖으로 벗어남.
  -> 근본 해결: 마커를 아예 제거. 오렌지색 "주행 경로" 선의 끝부분이
     자연스럽게 현재 위치를 나타내도록 단순화 (좌표계 불일치 문제 자체를
     제거, 별도 스케일링 계산 불필요).

[ 최종 구조 ]
- 컴포넌트 호출 2회로 고정 (시작/완료)
- 시작 호출: 배경(실루엣+전체경로) 1회 + 6초 주기 반복 재생 애니메이션
  (경로 끝까지 채우면 1초 홀드 후 재시작, requestAnimationFrame 기반)
- 완료 호출: 애니메이션 없이 실제 도달 지점까지 즉시 스냅
- 실제 진행률(%)과 예상 남은 시간은 progress_cb -> st.markdown/st.caption
  텍스트로 별도 표시 (컴포넌트와 분리, 반복 갱신 문제 없음)
- 지도가 먼저 로드된 뒤 퍼센트가 시작되도록 time.sleep(1)로 순서 조정

[ 배운 것 ]
Streamlit 커스텀 컴포넌트(그리고 plotly_chart 같은 무거운 요소 전반)는
"한 번의 스크립트 실행 안에서 여러 번 갱신"하는 용도로 설계되지 않음.
실시간처럼 보이는 갱신이 필요하면: (a) 호출 횟수를 최소화하고 나머지는
클라이언트 사이드 애니메이션으로 자체 처리하거나, (b) 진짜 반복 갱신이
필요한 부분은 st.text/st.markdown/st.progress 같은 가벼운 네이티브
요소로 분리하는 두 가지 전략을 병행하는 게 현실적인 해법.
