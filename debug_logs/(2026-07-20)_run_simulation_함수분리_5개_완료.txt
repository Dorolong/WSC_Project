(2026-07-20) run_simulation() 함수분리 나머지 5개 완료 (총 6/6)

[ 배경 ]
지난 세션(07-18)에서 착수한 run_simulation() 함수분리(계획 6개 중
1개, compute_lookahead만 완료)를 이번 세션에서 마저 진행. 사용자가
직접 에디터에서 코드를 작성하고, 세션 내내 자문(설계 검토/버그
지적)만 담당하는 방식으로 진행됨.

[ 2. compute_required_pace(step) ]
required_race_pace, required_next_cs_pace 계산. curr_dist/DY/HR/
next_cs/remaining_dist 전부 step에서 추출.
"compute_required_pace에 const 값이 들어갈 게 있나?"라는 질문에
분석: env_data 등 const는 불필요(전부 step 필드 + 전역
race.total_distance/race.CS_close_hour/drive.v_max/
drivable_hours_until만 사용, 이것들은 모듈 전역이라 인자로 안
넘겨도 함수 안에서 바로 접근 가능) - compute_lookahead()가 const를
필요로 하는 이유(env_data/route_dist 등 "이번 실행에 국한된 데이터")
와 대비됨.
초안 버그: next_cs 추출 누락(NameError), return이
required_race_pace를 빼먹는(튜플 1개만 반환) 버그 - 둘 다 지적 후
수정.

[ 3. compute_motor_derating(step) ]
전압 디레이팅(omega_wheel, backEMP_DC, omega_max -> v_max_derated).
prev_v/prev_V_terminal만 step에서 추출하는 순수 함수로 깔끔하게 완료.

[ 4. calender_handler(Accum_s) ]
원래 계획된 handle_calendar(Accum_s, DY, HR)에서 한 단계 더 통합:
"시간 추정"(total_s/DY/HR 계산)까지 이 함수 안으로 흡수해서 Accum_s
하나만 입력받도록 설계 변경.
설계 변경 과정: 처음엔 step["DY"]/step["HR"]를 인자로 받는 안이었으나,
"저거 remaining_dist는 state값으로 들어가야 하나" 등 여러 질문을
거치며 사용자가 직접 발견 - step["DY"]/step["HR"]는 루프 최상단
스냅샷이라 이번 스텝 dt 반영 후의 "진짜 현재 시각"보다 한 스텝
뒤처짐. 이를 지적하자 사용자가 스스로 "시간 추정"을 함수 안으로
합치는 재설계를 제안, 반영.
3-액션 리턴으로 설계: "Reset_Go"(야간 리셋, Accum_s만 갱신 후
continue) / "Stop"(27일 초과, break) / "Go"(정상 진행, Accum_s/
DY/HR/total_s 전부 반환). 처음엔 리셋과 정상진행을 둘 다 "Go"로
묶고 dict에 "Accum_s" 키 유무로 구분하려 했으나("이런식으로 쓰면
알아서 step에 들어가?" 등 mutable dict 대입 관련 질문 이후), 호출부
가독성 문제로 지적 후 액션명을 분리(Reset_Go/Go)함.

[ 5. control_stop_handler(...) ]
CS 도착/마감시각/구간평균속도 실격 체크 + cs_stop_simulation 호출.
"Fail"(실격, break) / "Stop"(정차 완료, 여러 값 갱신) / "Go"(CS
아님, 아무것도 안 바뀜) 3-액션.
**초안 버그 3종** (전부 지적 후 수정):
- visited_cs = set()로 함수 안에서 매번 새로 생성 -> 누적 방문
  기록이 매 호출마다 사라짐. visited_cs를 파라미터로 받아야 함
  (set은 mutable이라 .add()만 하면 리턴 없이도 호출부 원본에
  반영됨, Accum_s/soc 같은 스칼라와의 차이 - 이 세션 내내 반복
  등장한 "mutable vs 스칼라 carry-over" 구분이 여기서도 핵심).
- last_cs_dist/last_cs_time/Accum_s/soc를 파라미터로도 안 받고
  함수 내부에서 정의도 안 한 채 참조 -> NameError. 전부 파라미터로
  추가.
- CS 정차가 실제로 일어났을 때 갱신된 Accum_s/soc/DY/HR/total_s를
  리턴에 안 담아 호출부가 못 받는 문제 -> 리턴 dict에 추가.
- "Action": "Stop"이 calender_handler의 "Stop"(시뮬레이션 종료)과
  의미가 완전히 다른데 이름이 겹침(여기서는 "CS 정차 완료") - 서로
  다른 result 변수(cs_stop_result vs calender_result)에 담겨서
  실제 충돌은 없지만 가독성 문제로 지적, 사용자는 현재 이름 유지
  선택.
**호출 순서 버그**: 초안에서 env_row 조회(nearest_diff, DY, HR)가
control_stop_handler() 호출보다 먼저 있어서, CS 정차로 시간이 흘러
DY/HR이 바뀌어도 env_row는 정차 전 시각의 날씨를 씀(리팩터링 전
원본 코드는 CS 처리 -> env_row 조회 순서였음). 코드를 다시 확인해
달라는 요청("코드 다시 확인좀 해줘")에 정확한 위치를 찾아 지적,
순서 교정 완료.

[ 6. compute_vehicle_energy(step, soc, env_row, dt) ]
cal_route_vector/cal_drive_res/gen_solar/update_soc 호출 + P_net
계산 + prev_wind/heading 갱신을 한 함수로 통합, (soc,
prev_V_terminal, prev_wind_speed, prev_wind_dir, prev_heading)
튜플 반환.
**초안 버그**: 함수 시그니처에 soc가 없는데 내부에서
update_soc(soc, ...) 호출 -> NameError. step["soc"]로 대체해도
안 되는 이유까지 확인: step["soc"]는 루프 최상단 스냅샷이라 같은
iteration에서 CS 정차로 soc가 이미 갱신됐다면 stale한 값(DY/HR과
동일한 문제 패턴). soc를 명시적 파라미터로 추가해 호출 시점의
최신 bare soc를 넘기도록 수정.
이 과정에서 "v같은 값들은 iteration에 매 스텝 초기화되어서 새로운
값으로 계산되는거잖아?"라는 확인 질문이 나옴 - v 자체는 매 스텝
mpc_speed()로 새로 계산되니 맞지만, 그 v가 다음 스텝의 prev_v로
이어지는 다리 역할은 여전히 bare 변수가 담당해야 한다는 점을 재확인
(이 답변 도중 step["v"]로 전환하며 prev_v = v, dt 계산부의 bare v
참조가 깨진 것도 같이 발견/수정).

[ mpc_speed() state -> step 이름 통일 ]
함수 시그니처 mpc_speed(state, params) -> mpc_speed(step, params),
본문 내 state["..."] 21곳 전부 step["..."]로 일괄 변경. 호출부는
이미 mpc_speed(step, params) 형태였어서 이 변경으로 명명 일관성만
확보(동작 변화 없음). "mpc_speed 함수에 state 되어있는거 전부
step으로 바꿔줄 수있나" 요청으로 진행 - 이번 세션 중 몇 안 되게
사용자가 직접 편집이 아니라 나에게 편집을 요청한 케이스.
