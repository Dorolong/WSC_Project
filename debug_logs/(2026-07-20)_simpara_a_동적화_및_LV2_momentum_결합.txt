(2026-07-20) simpara.a 동적 변수화 + LV2 momentum 결합
================================================================

[ 배경 ]
progress/13 백로그 3번 항목("simpara.a 동적 변수화"). 기존엔
cal_drive_res()의 F_acc = physics.mass * a에서 a가 simpara.a(고정
상수 0.0)라, 실제 가감속에 따른 관성/운동에너지 효과가 시뮬레이션에
전혀 반영 안 됐음. LV2 slope look-ahead와 직접 연결되는 문제로,
a가 고정이면 "언덕 전에 미리 가속해서 관성으로 넘는다"는 효과가
모델에 없음.

[ 1. a 계산 위치 논의 ]
"이 중에서 가장 soc를 덜 쓰고 지나가는 알고리즘을 구성할 수 있나?"
질문에서 시작해, 물리적으로 뭐가 실제 SOC를 아끼는지 먼저 검토(아래
3번 참고). 이후 "근데 a 계산은 cal_drive_res 내에서 계산해서 return
하는 식으로 가져가도 되겠다"는 사용자 제안 - cal_drive_res(step, a,
wind_spd, wind_dir, car_dir) 형태로 a를 외부에서 받던 것을,
cal_drive_res가 step["v"]/step["prev_v"]/dt로 직접 a=(v-prev_v)/dt
를 계산해서 쓰고 그대로 리턴하는 형태로 변경. 이 판단이 가능했던
이유: step["prev_v"]가 mpc_speed() 계산에 이미 쓰인 "진짜 이전
스텝 속도"를 갖고 있어서(같은 iteration 안에서 bare prev_v가 이미
새 값으로 덮어써진 뒤에도 step["prev_v"]는 별개 dict 키라 안전),
별도의 bare 변수 추적 없이 step 하나로 a를 정확히 계산 가능.

[ 2. carry-over 배관 ]
step["a"]는 cal_drive_res가 계산하는 시점이 mpc_speed() 호출보다
뒤라 이번 스텝엔 못 쓰고 다음 스텝에만 반영 가능("나중에 경사도
반영 모델에 넣을 수 있도록 하려고" - 사용자가 이 타이밍 이슈를
먼저 인지하고 있었음). prev_a bare 변수를 만들어
compute_vehicle_energy() 호출 직후 prev_a = step["a"]로 갱신, 다음
iteration의 step 생성 시 a=prev_a로 시딩(다른 carry-over 변수들과
동일 패턴).
"직전이긴 한데 그래도 그렇게까지 급변할까 싶기도 하고. 2차 미분
항인데 그정도는 괜찮지 않을까"라는 사용자의 근사 타당성 판단에
동의 - v 자체가 이미 tanh 댐퍼로 스텝당 변화량이 제한돼 있어 그
변화율인 a도 스텝 간 급변하지 않고, 위치 기준 2차 미분항이라 원래
고차 미분일수록 신호가 매끈한 경향까지 더해져 한 스텝 지연된 근사가
무리 없다고 판단(이산 시간 제어의 backward difference 근사와 유사).
Configs/Vehicle_Params.py의 simpara.a도 simpara.prev_a로 개명해서
run_simulation()의 bare 변수명과 1:1 대응시킴.

[ 3. momentum 물리적 타당성 논의 (구현 전 검토) ]
"언덕 전에 가속 -> 관성으로 넘기기" 전략이 이 모델에서 실제로
SOC를 아끼는지 구현 전에 먼저 검토:
- F_slope/F_acc의 거리 적분은 고정된 시작/끝 속도·고도차에서는
  경로(속도 프로파일)와 무관 - momentum 자체가 공짜는 아님.
- F_aero ~ v^2(볼록함수)라 같은 평균속도(=같은 소요시간)면 균일한
  속도가 오히려 aero 손실이 최소(Jensen 부등식) - 속도를 들쭉날쭉
  하게 가져가는 건 그 자체로 약간의 손해.
- 결정적으로, **회생제동 효율(Regen_eff=0.6)이 40% 손실**이라
  "가속 후 회생으로 감속"하는 형태의 momentum은 순손실.
"그럼 언덕 정상까지는 가속하고 하강할 때는 회생제동을 끄고
탄력주행을 가자?"라는 사용자의 재정식화가 핵심을 정확히 짚음:
내리막에서 회생 없이 자연 가속(PE->KE 직접 전환, 손실 거의 없음)
-> 그 운동에너지로 다음 평지/오르막에서 모터 출력을 덜 쓰는 형태는
PE->전기(회생 60%)->다시 모터 방전 경로보다 변환 손실이 한 번 덜
끼어 유리함이 명확.
"근데 그러면 지금 회생제동 on/off를 제어해야하는데"라는 우려에
대한 정정: cal_drive_res()엔 별도 회생 스위치가 없고 P_tot<0이면
자동으로 회생 모드로 계산되는 구조라, "회생을 끈다"는 게 곧 "MPC가
내리막에서 필요 이상으로 감속을 요구하지 않게 하는 것"과 동일함을
확인 - 별도 on/off 제어 레이어를 새로 만들 필요 없이, LV2가 이미
slope_ahead<0(내리막)일 때 v를 올리는 방향으로 작동하고 있어서
그 경향을 momentum으로 보강하는 것으로 충분.
결론: 이론적으로 완전한 최적 여부는 언덕 형상/차량 스펙에 따라
달라 단정 어려움(진짜 최적화하려면 Pontryagin 최소원리/동적계획법
수준의 최적제어 문제) - 실용적으로는 회생 없는 자연 감속/가속을
허용하는 방향으로 구현하고 Optuna로 A/B 검증하기로 함.

[ 4. mpc_speed() LV2 반영 ]
slope_ahead > 임계값(오르막)일 때만 a 기반 페널티 완화 적용,
경계에서 값이 뚝 끊기지 않도록 하드 if 대신 스무스 램프 사용 -
"if slope_ahead > 0.03?" 하드 if 제안에 대해, 과거 LV8 하드스위치
경계값 버그 이력(debug_logs/(2026-07-13)_LV8_시간예산_설계.txt)을
근거로 스무스 램프 대안 제시, 사용자가 채택:
    slope_severity = clip((slope_ahead - 0.02) / 0.02, 0, 1)
    momentum = clip(a * momentum_gain, 0, 1) * slope_severity
    v -= slope_k * slope_ahead * (1 - momentum)
momentum_gain을 mpc_default_params에 신규 추가(기본값 1.0, 아직
Optuna 탐색공간엔 미포함).
