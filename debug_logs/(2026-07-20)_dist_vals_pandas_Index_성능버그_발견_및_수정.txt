(2026-07-20) dist_vals가 pandas Index라 느렸던 성능 버그 발견/수정
================================================================

[ 배경 ]
"저번까지 돌리던게 1분 안팎이었는데 갑자기 이렇게 튄다고? (Optuna
트라이얼 하나당 8분씩)"라는 질문에서 시작. 처음엔 "예전엔 트라이얼이
크래시/조기실격으로 일찍 끝났던 것 아니냐"는 가설을 세웠으나,
사용자가 "그 때도 완주율은 90%를 상회했었어"라고 반박 - 완주율이
비슷하다면 처리한 스텝 수도 비슷할 텐데 시간만 8배 차이나는 거라,
추측으로는 원인을 못 찾겠다고 판단하고 직접 프로파일링하기로 함.

[ 프로파일링 방법 ]
scripts/main.py와 동일한 데이터 로딩 과정을 재현한 스크립트를 만들어
cProfile로 run_simulation() 단일 호출(날씨 1개, K=1, 기본 파라미터)의
시간을 측정. 백그라운드로 실행.

[ 1차 프로파일링 결과 - 원인 발견 ]
route points: 151,932 / 완주율 80.0%(2,431,951m, 27일 초과로 종료) /
wall time: **214초**.
`compute_lookahead()` 하나가 전체 214초 중 **158초(74%)**를 차지.
자체 실행시간(tottime)은 10.7초뿐인데 cumulative는 158초 - 즉
compute_lookahead가 호출하는 다른 함수들에서 시간이 소모되고 있다는
뜻. 프로파일 상위 목록이 온통 pandas.core.indexes.base 관련 함수들
(__sub__, _arith_method, __array_ufunc__, argmin, sanitize_array,
isna, _isna_array 등)과 builtins.isinstance(2,365만 번 호출!)로
채워져 있음.

**근본 원인**: compute_lookahead()의 N-포인트 샘플링 루프 안에서
매번 다음을 실행:
    future_nearest = dist_vals[np.abs(dist_vals - future_dist_m).argmin()]
그런데 `dist_vals`가 numpy 배열이 아니라 **pandas Index 객체**
(scripts/main.py에서
`env_data.index.get_level_values("total_distance_m").unique().sort_values()`
로 생성, .to_numpy() 없이 그대로 사용 중이었음). pandas Index에
스칼라를 빼는(`-`) 연산은 numpy 배열 연산과 달리 pandas 내부의
타입체크·dtype추론·새 Index 객체 생성·isna 체크 등 훨씬 무거운
경로를 거침. 이 루프가 스텝당 N번(remaining_dist/70km 기준 보통
2~5회), 총 약 30만 번 호출되며 오버헤드가 누적됨.

**추정되는 발생 시점**: dist_vals 자체는 이번 세션 이전부터 pandas
Index였을 가능성이 높으나(코드 변경 이력 없음), compute_lookahead의
N-포인트 샘플링 루프는 07-17/07-18 세션에 "50km 앞 단일 지점 조회"
방식(스텝당 dist_vals 조회 1회)을 대체하며 도입된 기능(LV4+LV7
병합 작업). 즉 dist_vals가 pandas 타입이었던 기존 문제가, 스텝당
조회 횟수가 늘어나는 설계 변경(N-포인트 평균)과 맞물리며 증폭된
것으로 추정 - 오늘 세션의 함수분리 자체가 새로 만든 문제는 아님.

[ 수정 ]
scripts/main.py의 dist_vals 생성부에 `.to_numpy()` 추가:
    dist_vals = env_data.index.get_level_values("total_distance_m").unique().sort_values().to_numpy()
한 줄 수정으로 dist_vals가 순수 numpy 배열이 되어, 이후
`dist_vals - future_dist_m` 연산이 pandas 경로 대신 numpy 배열
산술을 타도록 함.

[ 2차 프로파일링 결과 - 검증 ]
동일 조건(같은 파라미터, 같은 route/env_data)으로 재측정:
wall time: **51.3초** (214초 대비 **4.2배 개선**).
완주율/거리(80.0%, 2,431,951m)와 처리 스텝 수(121,608행) 완전
동일 - 로직/결과에는 영향 없이 순수 속도만 개선됐음을 확인.
compute_lookahead()의 cumulative time이 158초 -> 12.9초로 급감.

[ 남은 병목 (참고, 미적용) ]
2차 프로파일 기준 다음 병목은 mpc_speed()(cumulative 21.5초) -
np.clip()을 스칼라 값 하나에 121만 번 넘게 호출하면서 numpy 함수
호출 자체의 오버헤드가 누적됨(numpy 스칼라 연산은 순수 파이썬
max()/min() 조합보다 오버헤드가 훨씬 큼 - 타입 디스패치 비용).
필요시 mpc_speed() 내부 np.clip() 호출들을 순수 파이썬
`max(min(x, hi), lo)`로 교체하면 추가 개선 가능하나, 4배 이상
개선된 현재 상태로 우선 충분하다고 판단해 이번엔 미적용.

거리/시간에 따라 달라짐). 다만 여전히 트라이얼당 수 분 단위라
