================================================================
(2026-07-13) LV8 다음CS 페이스 통합 및 버그 수정
================================================================

[ 배경 ]
기존 LV8은 "전체 완주 기준" 필요 페이스(required_race_pace) 하나만
보고 있었음. 그런데 실제 실격은 각 CS 개별 마감시각 기준이라, 전체
평균 페이스만으로는 "전체적으론 여유 있지만 특정 CS 구간 하나를
놓치는" 상황을 못 잡을 수 있다는 문제 제기. 오픈 시간(도착해도 대기만
하니 목표로 삼을 필요 없음)과 마감 시간(실격 기준)의 역할을 분리해서
설계하기로 함.

[ drivable_hours_until() 일반화 ]
기존 required_race_pace 계산이 "오늘 남은시간 + 남은날짜*9h"로
하드코딩되어 있었는데, 이걸 drivable_hours_until(DY, HR, target_h)
함수로 일반화. "지금부터 target_h(8/23 00시 기준 경과시간)까지
주행가능시간(08~17시 가정)"을 계산하는 범용 함수.
- 기존 공식이 이 함수의 target=day27 17시(113h) 특수 케이스와 정확히
  동일한 값을 낸다는 걸 확인 후 교체 (예: day23 08시 출발 기준 45시간).
- required_next_cs_pace 신설: 같은 함수를 next_cs의 CS_close_hour로
  호출. 마지막 CS(Port Augusta, 2720500m) 이후 구간은
  required_next_cs_pace = required_race_pace로 폴백 (다음 CS 자체가
  없으므로).

[ LV8 3항 가중평균 재설계 ]
mpc_controller.py의 LV8을 "전체 완주 페이스"와 "다음 CS 페이스" 두
신호로 확장:
    urgency_total = clip((required_race_pace - v)/v, 0, 1)
    soc_factor_total = clip((soc-soc_cutoff)/margin_total, 0, 1)
    global_factor = urgency_total * soc_factor_total

    urgency_next_cs = clip((required_next_cs_pace - v)/v, 0, 1)
    soc_factor_next_cs = clip((soc-soc_cutoff)/margin_next_cs, 0, 1)
    next_cs_factor = urgency_next_cs * soc_factor_next_cs

    total = 1 + global_factor + next_cs_factor
    v = (v + global_factor*required_race_pace
           + next_cs_factor*required_next_cs_pace) / total

margin 단일 파라미터를 margin_total/margin_next_cs로 분리해서 두 신호의
SOC 민감도를 독립적으로 튜닝 가능하게 함. v의 가중치는 항상 1(기준)이라
두 urgency가 전부 0이면(여유 있으면) 기존처럼 v 그대로 유지됨.

[ 버그 - 블렌딩 공식 오류 ]
사용자가 처음 작성한 버전은 가중치(global_factor, next_cs_factor)를
값(required_race_pace 등)과 혼동해서
    v = (v + global_factor**2 + next_cs_factor**2) / (v + global_factor + next_cs_factor)
형태였음. v(80대)에 비해 두 항(0~2 범위)이 무시할 수준이라 결과가
거의 1로 붕괴하는 심각한 버그. required_race_pace/required_next_cs_pace가
최종 식에 아예 등장하지 않는다는 점으로 발견. 위의 올바른 형태로 수정.

[ 그 외 버그 ]
- mpc_speed() 호출부/시그니처 인자 순서가 여러 차례 어긋남. 특히
  required_next_cs_pace, 이후 gen_ratio_std 추가 과정에서 호출부는
  앞쪽에 넣고 시그니처는 뒤쪽에 넣는 식으로 두 번 정도 어긋났음 ->
  자리별 대응표를 만들어 확인 후 정렬해서 해결.
- drivable_hours_until() 결과가 정확히 0이 되는 경우(예: DY=27,
  HR=17 - 마지막 날 마지막 유효 시각) required_race_pace/
  required_next_cs_pace 계산에서 RuntimeWarning: divide by zero
  발생. 원래 있던 "hours > 0.01이 아니면 drive.v_max로 폴백" 가드가
  리팩터링 과정에서 누락된 것으로 확인, 복원.
- mpc_controller.py 자체에서도 LV1~7 누적 보정(부호가 전부 음수로
  겹치는 극단적 경우)으로 v가 0 이하까지 내려갈 수 있어, LV8의
  (required_race_pace - v)/v 계산에서 별도로 divide-by-zero 발생.
  LV8 진입 직전에 `v = max(v, params.get("v_min", 45))` 클램프 추가로
  해결.
