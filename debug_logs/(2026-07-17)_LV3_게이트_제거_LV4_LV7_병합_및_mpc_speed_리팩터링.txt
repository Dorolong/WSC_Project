(2026-07-17) LV3 게이트 제거, LV4+LV7 병합, mpc_speed 리팩터링,
파라미터 이름 전면 개편

[ 배경 ]
LV4(에너지 예산 보정)와 LV7(미래 일사량 추세 보정)이 본질적으로
같은 목적(향후 발전량을 근거로 감속 여부 판단)을 서로 다른 방식
(현재 시점 기준 vs 50km 앞 단일 지점 기준)으로 각각 계단형으로
처리하고 있어 병합 필요성 논의.

[ LV3_radi_soc_min 게이트 제거 ]
기존 목적: "낮은 SOC에서 일사량이 좋으면 속도를 밟아버리는" 문제
방지용 SOC 기준 on/off 게이트.
검토 결과: LV1이 ramp 전환되며 soc_ramp_low(~0.28)가 기존
LV3_radi_soc_min(0.3)과 거의 겹쳐서, LV3가 개입하는 시점엔 이미
LV1이 v를 v_min 쪽으로 강하게 눌러놓은 상태 -> 게이트가 상당 부분
중복. soc_cutoff 하드컷 + LV8 페이스 블렌딩도 별도 안전판으로
존재. LV3 ramp 전환 자체는 이 문제를 직접 해결하진 않지만(게이트와
반응곡선은 별개 문제), 다른 안전장치들과의 중복성을 근거로 게이트
제거 결정. 실제 행동 변화이므로 다음 탐색 결과에서 저SOC+고일사량
구간 모니터링 필요.

[ LV4+LV7 병합 설계 - 3가지 옵션 검토 ]
1) 단순평균: 기존 고정 50km 앞 단일 지점 future_gen_ratio와 현재
   gen_ratio 단순평균
2) 동적 lookahead: 50km 고정 대신 remaining_dist(다음 CS까지 거리)
   지점에서 조회
3) 다중 지점 가중평균: remaining_dist를 N등분해서 여러 지점을
   샘플링, 거리역수 가중치로 평균
사용자가 3번 선택. 단, "다른 레벨에서 파라미터를 최대한 줄이는
방식으로 가야 한다"는 전제 조건 제시(3번이 파라미터/연산 비용을
늘리는 방향이라 상쇄 필요).

[ 파라미터 감축 방안 ]
- LV4_energy_crit(기존 자유 탐색값)를 leg_dist_km 기반으로 해석적
  유도: energy_crit = (soc_start_min - soc_cutoff) / leg_dist_km
  (leg_dist_km = 직전 CS ~ 다음 CS 실제 leg 길이)
- 실제 CS 구간 거리 계산 결과 편차가 큼(198km~487km, 평균 303.8km) ->
  평균값 근사 대신 leg별 실제 값 사용하기로 결정
- N-포인트 샘플링 간격도 탐색 파라미터로 만들지 않고 고정 상수
  (target_spacing_km)로 하드코딩하기로 결정
- 결과적으로 LV4_energy_crit, LV7_trend_crit, LV7_look_ahead_para,
  LV7_look_ahead_dist, LV3_radi_soc_min 5개 파라미터 순감소, 신규
  탐색 파라미터 없음(에너지 관련은 energy_v 하나만 유지)

[ target_spacing_km 값 결정 근거 ]
env_data.csv 확인 결과: 거리 그리드 약 10km 간격(촘촘함), 시간(HR)은
1시간 단위(정수, 7~18)뿐 -> 정보의 실질적 병목은 시간 해상도.
순항속도(기존 best trial 기준 70~90km/h)로 보면 1시간 이동거리가
약 70~90km. 50km 간격은 이보다 촘촘해서 인접 샘플 지점이 같은
시간대(같은 날씨 스냅샷)에 중복 조회될 가능성이 있음 판단 ->
target_spacing_km=70으로 결정(50 대신).

[ N-포인트 다중 샘플링 최종 설계 ]
    N = max(1, round(remaining_dist / target_spacing_km))
    (k=0: 현재 지점, k=1..N: remaining_dist를 N등분한 각 지점)
    weight_k = 1 / (k+1)   # 등간격이라 인덱스 자체가 거리에 비례,
                           # 실제 km 계산 없이 인덱스만으로 거리역수
                           # 가중치 근사 가능
    avg_gen_ratio = sum(gen_ratio_k * weight_k) / sum(weight_k)
leg 길이에 비례해서 N이 자동으로 늘어나(짧은 leg는 성기게, 긴 leg는
촘촘하게), 300km/200km 식의 임의 구간 경계값을 따로 관리할 필요가
없어짐.

[ mpc_speed() 인자 구조 리팩터링 - state dict 도입 ]
배경: mpc_speed()가 인자 14개까지 늘어났고, 새 파라미터(
required_next_cs_pace, gen_ratio_std 등) 추가될 때마다 호출부와
인자 순서가 반복적으로 어긋나는 버그가 있었음.
검토 과정:
- dataclass안: 오타/누락을 그 자리에서 에러로 잡아준다는 장점이
  있으나, 순서 안전성 자체는 dict(key=value) 키워드 생성으로도
  동일하게 확보됨을 확인 -> 기존 params dict 스타일과 통일성을
  위해 dataclass 대신 plain dict 채택
- 정의 위치: 별도 스키마가 없는 plain dict라 "선언"이 따로 없고,
  Vehicle_Function.py의 run_simulation() 루프 안에서
  state = dict(soc=soc, slope=curr_slope, ...) 형태로 매 스텝
  생성과 동시에 값이 채워짐. mpc_speed(state, params)로 전달.
- params(튜닝 계수)는 기존처럼 params.get(key, default) 유지,
  state(필수 데이터)는 state["key"]로 바로 인덱싱(기본값 없이 -
  누락 시 KeyError로 바로 드러나야 하는 게 의도된 동작).

[ 구현 중 발견/수정된 버그들 ]
1) avg_gen_ratio 미정의: state dict에서 참조하는데 계산 로직 자체가
   빠져있어 NameError
2) leg_dist_km 정의 순서/의미 충돌: LV4용(직전CS~다음CS leg 전체
   길이, next_cs-last_cs_dist)과 기존 실격체크용(직전CS~현재까지
   주행거리, curr_dist-last_cs_dist)이 같은 이름을 쓰면서 후자가
   더 뒤에서 정의돼 UnboundLocalError 발생 + 의미 충돌 -> 후자를
   leg_dist_goto로 이름 분리
3) N 계산 연산자 우선순위 오류: N = max(1, round(remaining_dist) /
   target_spacing_km) (round()가 remaining_dist에만 걸림 -> float
   결과 -> range(1, N+1)에서 TypeError) -> round()를 나눗셈 전체에
   걸리도록 괄호 수정
4) env_data.get() 튜플 누락: env_data.get((future_nearest),
   future_DY, future_HR) (괄호가 튜플이 아니라 인자 3개로 풀림 ->
   dict.get()이 인자 2개까지만 받아 TypeError) -> 튜플로 확실히
   묶음
5) staet 오타: state["gen_ratio"]를 staet["gen_ratio"]로 오타 ->
   NameError, 수정
6) LV8 블록(state 리팩터링 이전 잔존 bare 변수): soc,
   required_race_pace, required_next_cs_pace, v_max_derated,
   prev_v가 함수 인자 제거 이후에도 bare로 남아있던 것 전부
   state["..."]로 교체

[ 파라미터 이름 전면 개편 - LV 번호 기반 -> 역할 기반 ]
사용자 제안: LV 번호는 로직 순서가 바뀔 때마다(이번 LV4+LV7 병합처럼)
다시 매겨야 하는 문제가 있어 역할 기반 이름으로 전환.
  LV1_V1 -> v_soc_high
  LV1_soc1 -> soc_ramp_high, LV1_soc2 -> soc_ramp_low
  LV2_slope_k -> slope_k
  LV3_radi_para -> radi_para, LV3_radi_risk -> radi_risk
  LV4_energy_v -> energy_v (처음에 energy_V로 오타났던 것 재수정)
  LV5_winddir_para -> winddir_para
  margin_total, margin_next_cs, soc_cutoff, v_rate_limiting, v_min은
  기존에도 번호 없이 있었으므로 변경 없음
mpc_default_params 딕셔너리, mpc_speed() 본문의 params.get() 호출부,
scripts/main.py의 trial.suggest_*() 전부 동기화 필요(세 곳 중 한
곳이라도 이름이 안 맞으면 조용히 기본값으로 fallback되는 위험이
있어 한 번에 맞춤).
