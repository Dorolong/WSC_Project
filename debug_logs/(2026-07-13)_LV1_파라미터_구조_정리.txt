================================================================
(2026-07-13) LV1_V1~V3 탐색 구간 겹침 문제
================================================================

[ 문제 ]
scripts/main.py의 Optuna 탐색 구간:
    LV1_V1: suggest_int(60, 100)
    LV1_V2: suggest_int(50, 90)
    LV1_V3: suggest_int(40, 80)
서로 겹쳐있어서 "V3 > V1"(SOC 낮을 때 오히려 더 빠르게 가는) 같은
전략적으로 말이 안 되는 조합까지 탐색 공간에 포함됨. 실제로 이전 라운드
best_params에서 LV1_V2와 LV1_V3가 둘 다 63으로 나온 사례 확인 -> 이걸
계기로 문제 발견.

[ 해결 1차 - 고정 구간 재분배 ]
V1(70-100) > V2(50-70) > V3(0-50)로 겹치지 않게 재설정.

[ 해결 2차 - LV1_V3 자체를 제거 ]
V3(최하위 SOC 티어 속도)와 v_min(최종 속도 하한선)이 사실상 같은 개념인데
따로 탐색되고 있었음. V3 < v_min인 조합은 최종 클리핑(v = max(v, v_min))
때문에 V3 값 자체가 의미 없어져서 탐색 공간 낭비.
-> mpc_controller.py의 LV1 최하위 티어 분기를 params.get("v_min")으로
   직접 대체, LV1_V3 파라미터 완전 삭제 (mpc_default_params, Optuna
   탐색 공간 둘 다에서 제거).

[ 해결 3차 - V2 vs v_min 사이 같은 문제 재발 가능성 ]
LV1_V3 제거 후에도 V2(50-70 고정 구간)와 v_min(20-60 고정 구간)이 서로
독립적으로 샘플링되면 v_min > V2인 조합이 또 나올 수 있음(예: v_min=58,
V2=52). 이번엔 구간을 또 수동으로 맞추는 대신 근본적으로 해결:
    v_min = suggest_int("v_min", 20, 60)
    LV1_V2 = suggest_int("LV1_V2", v_min, 100)   # v_min 이상으로 강제
    LV1_V1 = suggest_int("LV1_V1", LV1_V2, 100)  # V2 이상으로 강제
순차 샘플링으로 전환해서 v_min <= V2 <= V1 <= 100이 어떤 값이 나오든
구조적으로 항상 보장되게 함. 같은 종류의 겹침 버그가 이걸로 세 번째라
땜질보다 구조적 해결을 선택.

[ 트레이드오프 검토 ]
전체 범위를 열고 순서 제약만 거는 방식이 탐색 공간을 넓혀서(고정 구간
대비 조합 수 약 2~3배) 더 많은 트라이얼이 필요해지는 단점이 있음.
"경계 자체를 변수로 만들기"(cut point 방식)도 검토했으나 순서 제약
방식과 사실상 동일한 탐색 공간이라 실익 없다고 판단. 지금은 완주
사례가 아직 안정적으로 쌓이지 않은 단계라 탐색 효율을 우선시.

[ 관련 파일 ]
mpc/mpc_controller.py, scripts/main.py

[ 상태 ]
완료. app.py의 관련 슬라이더/session_state 참조(LV1_V3 관련 3곳)도
동기화해서 수정함 (KeyError 방지).
