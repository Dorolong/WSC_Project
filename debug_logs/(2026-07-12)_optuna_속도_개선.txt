================================================================
(2026-07-12) Optuna 트라이얼 속도 개선
================================================================

[ 문제 ]
Optuna 트라이얼 1회당 2분 이상 소요 (이전 컴퓨터에서는 1분 내외).
원인 분석 결과 컴퓨터 성능 차이가 아니라 코드 구조 문제로 판단.

[ 원인 ]
Functions/Vehicle_Function.py의 run_simulation()이 매 스텝마다
env_data.loc[(dist, DY, HR)] 형태의 MultiIndex 조회를 최대 3번
(현재 위치 / LV7 미래 예측 / Control Stop 정차) 수행함.

route가 약 15만 행이라 트라이얼 1회당 pandas .loc 호출이 40만 회 이상
발생하고, 호출마다 튜플 해싱 + Series 객체 생성 오버헤드가 누적됨.
추가로 pandas 1.3.5 -> 3.0.3 버전업(새 PC venv 구성 과정에서 발생)으로
이런 스칼라성 .loc 접근의 건당 오버헤드가 더 커졌을 가능성도 있음.

[ 해결 방향 ]
env_data(DataFrame, MultiIndex)를 아래처럼 dict로 변환해 O(1) 조회로 전환.
    env_dict = env_data.to_dict("index")
    # {(dist, DY, HR): {"shortwave_radiation": ..., "wind_speed_10m": ..., ...}}

dict-of-dict 구조라 기존 env_row["shortwave_radiation"] 같은 컬럼명 접근
코드는 그대로 재사용 가능. .loc[튜플] -> .get(튜플)로만 교체.
rad_max(발전 비율 계산용 최댓값)는 컬럼 최댓값이라 dict 변환 전 DataFrame에서
한 번만 계산해 별도 인자로 넘기도록 함수 시그니처 변경.

[ 변경 대상 ]
- Functions/Vehicle_Function.py
    cs_stop_simulation(): env_data.loc + try/except KeyError -> env_dict.get() + None 체크
    run_simulation(): 시그니처에 rad_max 인자 추가, 3곳의 .loc 조회를 .get()으로 교체
- scripts/main.py
    env_dict, rad_max 생성 후 run_simulation() 호출 시 env_dict 전달
- app.py
    load_data() 안에서 env_dict, rad_max 생성 후 반환값에 포함,
    run_simulation() 호출 시 env_dict 전달

[ 적용 상태 (2026-07-12 기준) ]
Functions/Vehicle_Function.py: 정상 적용 확인.

scripts/main.py, app.py: 적용 중 버그 발견, 아직 미해결.
  1) scripts/main.py - rad_max를 env_dict 기준으로 계산 (env_dict["shortwave_radiation"].max())
     -> dict는 컬럼명 키가 없어 KeyError. env_data(DataFrame) 기준으로 계산해야 함.
  2) scripts/main.py - objective() 안 run_simulation() 호출에 env_data를 그대로 전달

  3) scripts/main.py - 마지막 best_params 재실행 호출이 구 시그니처 그대로
     (rad_max 인자 누락 + env_data 전달) -> TypeError 발생 예상.
  4) app.py - load_data()가 env_dict를 만들어놓고 return에는 env_data를 반환

        에러 없이 실행되지만 모든 조회가 None 반환 (조용히 깨지는 버그).
  5) (최적화와 무관, 별도 발견) app.py의 "평균 발전량" 지표 추가 과정에서

[ 2차 최적화 ] route.iloc() 제거 (numpy 배열 전환)
================================================================

[ 배경 ]
dict 캐싱 적용 후 실측 1분 13초/trial. env_data 조회(45만 회) 병목은
해소됐지만, run_simulation() 안에서 매 스텝 route.iloc[i-1], route.iloc[i]로
새 Series 객체를 만드는 부분(스텝당 2회, 총 30만 회)이 같은 종류의 오버헤드로
남아있다고 판단해 추가 최적화 진행.

[ 해결 방향 ]
route(DataFrame)를 컬럼별 numpy 배열 dict로 미리 변환해서 전달.
    route_np = {
        "dist":  route["total_distance_m"].to_numpy(),
        "lat":   route["lat"].to_numpy(),
        "lon":   route["lon"].to_numpy(),
        "slope": route["slope"].to_numpy(),
        "theta": route["theta"].to_numpy(),
    }
run_simulation() 안에서 route.iloc[i]로 매번 Series를 새로 만드는 대신
numpy 배열 인덱싱(route_dist[i] 등)으로 대체.

주의: 원본 코드는 prev/curr를 루프 상단에서 미리 캡처해두고 그 아래서
i += 1이 일어나도 prev/curr 값 자체는 안 바뀌는 구조였음. 이를 그대로
route_dist[i] 식으로 바꾸면서 i += 1 아래쪽에서도 route_xxx[i]를 계속
쓰면, 이미 증가된 i를 참조하게 되어 엉뚱한 행을 가리키는 버그가 생길
수 있었음. 이를 피하기 위해 curr_dist, prev_dist, curr_lat/lon,
prev_lat/lon, curr_slope, theta를 루프 최상단에서 전부 지역변수로
캡처해두고 이후 코드에서는 그 변수만 사용하도록 작성.

[ 변경 대상 ]
- Functions/Vehicle_Function.py
    run_simulation(): route.iloc[] 전량 제거, route_dist/lat/lon/slope/theta
    numpy 배열 인덱싱 + 루프 상단 지역변수 캡처 패턴으로 재작성
- scripts/main.py, app.py
    route_np(numpy 배열 dict) 생성 후 run_simulation() 호출 시 route 대신
    route_np 전달 (nearest_map 생성용 route 원본 DataFrame은 그대로 유지)
