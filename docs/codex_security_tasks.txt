확인해서 적은 것이니 추측하지 말고 이 값을 기준으로 삼되,
착수 시점에 코드가 바뀌었을 수 있으니 한 번은 대조할 것.

- 서버: uvicorn 단일 프로세스(--workers 없음). server/wsc-launcher.service
  ExecStart 참고. **워커가 1개라서 메모리 기반 카운터를 써도 일관된다.**
  (나중에 워커를 늘리면 이 전제가 깨진다 - 작업 1에 주석으로 남길 것)
- 프록시: Caddy -> 127.0.0.1:8000. uvicorn 이 --proxy-headers
  --forwarded-allow-ips 127.0.0.1 로 떠 있어서 **request.client.host 가
  이미 진짜 접속자 IP** 다. X-Forwarded-For 를 직접 파싱하지 말 것
  (직접 파싱하면 헤더 위조로 우회당한다).
- 인증: 브라우저가 Supabase 와 **직접** 로그인한다. 우리 서버는 로그인
  요청을 받지 않는다. 서버는 verify_user() 에서 받은 access token 을
  Supabase /auth/v1/user 로 확인만 한다(server/main.py:313).
  -> **"로그인 레이트 리밋"은 우리 서버 소관이 아니다.** 백로그에
     "로그인·실행 요청을 무제한으로 때릴 수 있다"고 적혀 있는데,
     로그인은 Supabase 쪽이다. 우리가 지켜야 할 것은 (a) 서버 CPU/대기열,
     (b) 우리가 Supabase 로 내보내는 verify 호출량이다.
- 엔드포인트: /api/status, /api/my-active-run, /api/runs(POST),
  /api/runs/{id}, /api/sim/runs(POST), /api/sim/my-active-run,
  /api/sim/runs/{id}, /api/sim/runs/{id}/figure, /api/sim/runs/{id}/csv,
  /api/sim/route, /api/sim/default-config. 나머지 경로는 StaticFiles.
- 프론트 폴링 실측 주기:
    js/auth.js:73       /api/status          4000ms
    js/auth.js:77       /api/my-active-run   3000ms
    js/simulator.js:127,172  시뮬 진행률     1500ms
  -> 시뮬레이션 도는 동안 **한 사용자가 분당 약 75건**을 정상적으로
     보낸다(0.25+0.33+0.67 req/s). 탭을 2개 열면 150건이다.
- 동시 실행 제한: WSC_MAX_CONCURRENT=1(Optuna), WSC_MAX_SIM_CONCURRENT=2.
  즉 **연산 자체는 이미 대기열로 보호**돼 있다. 안 막힌 것은 "대기열에
  쓰레기를 무한히 쌓는 것"과 "폴링으로 서버를 때리는 것"이다.
- anon key: server/static/sync-config.js 가 **브라우저로 그대로 내려간다.**
  즉 이 값은 구조상 공개값이다(작업 3에서 다시 설명).

작업 1 - 레이트 리밋
================================================================
[ 문제 ]
공개 도메인이라 스캐너가 붙는다. progress/48 에 "스캐너 probe 가 실제로
로그에 잡히고 있다"고 기록돼 있다. 현재 어떤 경로에도 요청 수 제한이
없다. 위험은 두 가지다.
 (a) POST /api/runs, POST /api/sim/runs 를 반복 호출해 **대기열을
     쓰레기로 채우는 것**. 연산 동시성은 막혀 있지만 큐 길이는 안 막혀
     있고, 각 항목이 메모리와 상태 파일을 먹는다.
 (b) 아무 /api/* 나 초당 수천 번 때려 **서버를 마비**시키는 것. 특히
     verify_user() 가 붙은 엔드포인트는 요청마다 Supabase 로 나가는
     외부 호출이 하나씩 생긴다 - 우리 서버보다 Supabase 쿼터가 먼저
     터질 수 있다.

[ 하지 말 것 - 먼저 검토하고 기각한 안 ]
Caddy 의 rate_limit 은 **표준 배포에 없는 서드파티 모듈**이라
xcaddy 로 Caddy 를 다시 빌드해야 한다. 서버 SSH 작업이 늘고 Caddy
업그레이드마다 재빌드가 필요하다. **채택하지 말 것.**
-> FastAPI 미들웨어로 구현한다.

[ 요구사항 ]
 1-1. server/ 에 레이트 리밋 미들웨어를 추가한다. 새 파일
      `server/rate_limit.py` 로 분리할 것(main.py 가 이미 900줄 근처다).
 1-2. **정적 파일 경로에는 걸지 말 것.** `/api/` 로 시작하는 경로만
      대상으로 한다. index.html·css·js 는 캐시되고 양도 적다.
 1-3. 제한을 **두 종류**로 나눈다. 하나로 뭉치면 정상 폴링이 막힌다.
      (A) 일반 /api/* (주로 GET 폴링)
          - 키: 접속자 IP (request.client.host)
          - 기본값: **분당 300건**
          - 근거: 실측 정상 사용량이 사용자당 분당 약 75건이다(0-1절).
            팀원이 같은 공유 IP(학교/회사 NAT) 뒤에 있을 수 있으므로
            여유를 4배로 둔다. 이 숫자는 환경변수로 바꿀 수 있어야 한다.
      (B) 실행 생성 POST (/api/runs, /api/sim/runs)
          - 키: **IP 가 아니라 user_id**. 이유: 팀원들이 같은 NAT 뒤에
            있으면 IP 기준으로는 서로의 몫을 잡아먹는다. 이 두 경로는
            어차피 인증이 필요하므로 user_id 를 쓸 수 있다.
          - 기본값: **시간당 20건**
          - 근거: 한 번 실행이 수 분~수십 분이고 동시 실행은 1~2로
            제한돼 있다. 정상 사용자가 시간당 20번을 넘길 이유가 없다.
 1-4. 초과 시 **429** 와 `Retry-After` 헤더(남은 초)를 반환한다.
      본문은 기존 에러들과 같은 형식(detail 한국어 문장)으로.
 1-5. 모든 수치를 환경변수로 조절 가능하게 한다. 기본값은 위와 같다.
        WSC_RATELIMIT_ENABLED      (기본 "1", "0" 이면 전체 비활성)
        WSC_RATELIMIT_API_PER_MIN  (기본 300)
        WSC_RATELIMIT_RUN_PER_HOUR (기본 20)
      **비활성 스위치(ENABLED)를 반드시 넣을 것** - 배포 후 정상 사용자가
      막히는 사고가 나면 코드 배포 없이 systemd 환경변수만 고쳐서 즉시
      끌 수 있어야 한다.
 1-6. 429 가 발생하면 로그에 남긴다(경고 레벨, 키와 경로 포함).
      **키가 user_id 인 경우에도 토큰은 절대 남기지 말 것.**

[ 설계 요구사항 ]
 1-7. 알고리즘은 **고정 윈도가 아니라 슬라이딩 윈도**를 쓸 것.
      고정 윈도는 경계에서 두 배가 통과한다(59초에 300건, 61초에 또
      300건). deque 에 타임스탬프를 넣고 윈도 밖을 버리는 방식이면 충분하다.
 1-8. 메모리 누수 방지: 키가 무한히 쌓이지 않게 주기적으로(또는 접근 시)
      오래된 키를 제거할 것. 스캐너는 매번 다른 IP 로 올 수 있다.
 1-9. 워커 1개 전제를 **코드 주석으로 남길 것**. "uvicorn --workers 를
      2 이상으로 올리면 이 카운터가 워커별로 따로 세어져 실효 한도가
      워커 수만큼 늘어난다. 그때는 Redis 등 공유 저장소가 필요하다."
 1-10. 미들웨어 순서 주의: 기존 log_requests 미들웨어와의 순서를 확인하고,
       **429 도 로그에 남게** 할 것.

[ 검증 (게이트 B) ]

작업 2 - RLS/GRANT 전수 점검 + 스키마 SQL 문서화
================================================================
[ 문제 ]
progress/48 에서 optuna_runs 조회가 401 이 나던 원인이 **테이블에
authenticated 역할 GRANT 가 없어서**였다. 그때 얻은 교훈이 중요하다:

    RLS 정책이 없으면      -> 빈 배열 200
    테이블 GRANT 가 없으면 -> 401

즉 두 겹(GRANT + RLS)이 다 있어야 하는데, 한 테이블에서 빠져 있었다는
것은 **다른 테이블도 확인할 값어치가 있다**는 뜻이다.

[ 문서 불일치 - 이번에 같이 고칠 것 ]
progress/48 은 "SETUP.md 에 create table + grant + RLS 정책 전체를
정리했다"고 적어놨는데, **실제로는 안 들어가 있다.** 확인 결과:
 - SETUP.md 의 이번 변경분은 uvicorn 실행 명령 3줄뿐이다
 - 레포 전체에 create policy / grant / enable row level security 문자열이
   하나도 없다
 - SETUP.md 75~78 줄은 여전히 "스키마는 debug_logs 에서 검색하거나
   Claude 에게 요청"이라고 되어 있다
-> **Supabase 를 새로 구축해야 하면 지금은 코드에서 역추적하는 수밖에
   없다.** 이번 작업에서 실제로 문서화한다.

[ 요구사항 ]
 2-1. `docs/supabase_schema.sql` 을 새로 만든다. 아래 3개 테이블의
      create table + grant + RLS enable + policy 를 **재실행 가능한
      형태**로 담는다(create table if not exists, drop policy if exists
      후 create policy 등). 대상 테이블:
        - simulation_runs
        - user_settings
        - optuna_runs
      컬럼은 코드에서 실제 쓰는 것을 근거로 확정할 것:
        server/main.py, server/study_runner.py, server/sim_runner.py,
        app.py, shared/cfg_serde.py 에서 .table("...").select/insert/
        upsert 하는 부분을 전부 찾아 대조한다.
      **추측으로 컬럼을 만들지 말 것.** 근거가 되는 파일:줄을 SQL 주석으로
      남길 것.
 2-2. 점검용 SQL 도 같은 파일 아래쪽에 "확인 쿼리" 절로 넣는다.
      최소한 다음 3가지를 볼 수 있어야 한다:
        (a) RLS 가 켜져 있는 테이블 목록      (pg_tables / pg_class.relrowsecurity)
        (b) 테이블별 정책 목록               (pg_policies)
        (c) authenticated 역할의 테이블 권한 (information_schema.role_table_grants)
 2-3. SETUP.md 의 Supabase 절을 고친다. "debug_logs 에서 검색하거나
      Claude 에게 요청" 문구를 지우고 docs/supabase_schema.sql 을 가리키게
      한다. 통합 웹(server/)도 같은 Supabase 를 쓴다는 점을 명시한다.
 2-4. progress/48 의 잘못된 서술을 정정한다. **기록을 지우지 말고**,
      "[2026-08-XX 정정] SETUP.md 정리는 실제로는 누락됐고
      docs/supabase_schema.sql 로 이번에 처리함" 형태로 덧붙일 것.

[ 작업 주체 - 중요 ]
 2-5. **실제 SQL 실행과 대시보드 확인은 Codex 가 못 한다.** Supabase
      SQL Editor 는 사용자만 쓸 수 있다. Codex 는 (1) SQL 파일 작성,
      (2) 확인 쿼리 작성, (3) 사용자가 붙여넣을 실행 순서를 보고서에
      정리하는 데까지 한다.
 2-6. 보고서에 **"사용자가 실행할 것" 절을 따로** 만들고, 확인 쿼리의
      기대 결과(예: 3개 테이블 모두 rowsecurity=true, 각 테이블에 정책

[ 먼저 바로잡을 오해 ]
백로그에 "anon key 하드코딩"이 보안 항목으로 적혀 있는데, **이 키는

   아니라 다음 두 가지다:
   (a) 키를 회전(rotate)했을 때 서버가 낡은 키를 조용히 계속 쓰는 것 방지
   (b) 이 값이 "공개돼도 되는 값"임을 문서에 못 박아, 나중에 누가
       service_role 키를 같은 자리에 넣는 사고를 막기

[ 요구사항 ]

      명확한 메시지와 함께 즉시 실패(fail fast)할 것. 요청이 들어온

작업 6 - HSTS 1주 -> 1년  **(이번에 하지 말 것)**
================================================================
[ 왜 지금이 아닌가 ]
Caddyfile 에 이미 "몇 주 안정적이면 1년(31536000)으로 올릴 것"이라고
적혀 있고, 1주일로 올린 날이 **2026-08-05** 다. 아직 하루도 안 지났다.

HSTS 는 **되돌리기 비싼 설정**이다. max-age 를 1년으로 박아두면, 그
사이 인증서가 깨졌을 때 이미 방문했던 사용자는 1년 동안 우회 접속이
불가능하다(경고 무시 버튼도 안 나온다). 그래서 "며칠 잘 돌았다"가 아니라
"**인증서 자동 갱신을 한 번 이상 통과했다**"가 진짜 기준이다.
Let's Encrypt 인증서는 90일이고 Caddy 는 만료 30일 전쯤 갱신한다.

[ 조건 ]
다음이 모두 참일 때 올린다:
 6-1. 최소 2~3주간 인증서/접속 문제 없음
 6-2. **자동 갱신이 최소 1회 성공**한 것을 로그로 확인
      (journalctl -u caddy 에서 갱신 기록)
 6-3. 그 사이 도메인(DuckDNS) 주소를 바꿀 계획이 없음

[ 이번에 할 것 ]
 6-4. 위 조건과 판단 근거를 **progress 문서와 Caddyfile 주석에 명확히**
      남긴다. 다음 세션이 "몇 주 지났으니 올리자"가 아니라 "갱신 1회
      통과했나?"로 판단할 수 있게. 값 자체는 건드리지 말 것.
 6-5. preload 는 붙이지 말 것(이미 Caddyfile 주석에 있는 이유 그대로).
