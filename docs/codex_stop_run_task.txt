1. 설계 - 죽이지 말고 "협조적 중단"
================================================================
[ 기각한 안 - 프로세스 kill ]
SIGKILL/terminate 로 바로 죽이면:
 - 진행 중이던 trial 이 통째로 버려진다(1~2분 계산이 증발)
 - Supabase 에는 20 배수까지만 남아 **최대 19개 trial 손실**
 - 결과 JSON 이 없어 결과 카드가 안 뜬다
 - study sqlite 가 남아 디스크를 먹는다
-> 사용자 요구사항이 "그만큼을 **저장**"이므로 이 안은 요구를 못 맞춘다.
   **채택하지 말 것.**

[ 채택 - study.stop() 협조적 중단 ]
Optuna 의 study.stop() 을 **콜백 안에서** 호출하면, 현재 trial 을 끝까지
마친 뒤 optimize() 루프가 정상 반환된다. 그러면 study_runner 의 기존
후처리 경로(best 계산 -> 체크포인트 -> 결과 JSON -> db 정리)가 그대로
실행된다.

    [중단] 버튼
      -> 서버가 취소 플래그 파일 생성
      -> study_runner 의 매-trial 콜백이 플래그 확인 -> study.stop()
      -> 진행 중이던 trial 은 **완료된 뒤** 루프 종료
      -> 기존 후처리 경로 실행 (status="stopped")

**장점**: 새 코드가 거의 필요 없다. 콜백(study_runner.py:89)과 후처리
경로(:191~220)가 이미 있다.
**대가**: 즉시 안 멈춘다. 최대 trial 1개 시간(서버 기준 90초 안팎).
-> UI 로 설명하고(요구사항 3-4), 안전장치로 강제 종료를 둔다(2-5).

[ 왜 시그널이 아니라 플래그 파일인가 ]
study_runner 는 chunk 단위 while 루프 안에서 optimize() 를 반복 호출한다.
시그널 핸들러로 하면 "지금 어느 지점인지"에 따라 처리가 갈려 복잡해진다.
플래그 파일은 콜백에서 한 줄로 확인되고, 서버 재시작에도 살아남으며,
디버깅 때 눈으로 확인할 수 있다. **플래그 파일을 쓸 것.**

4. 검증 (게이트 B)
================================================================
로컬에서 서버를 띄우고 확인한다. **trial 수를 작게(예: 3~5) 잡고
CHECKPOINT_EVERY 를 2 정도로 낮춰서** 체크포인트 경계를 빠르게 볼 것.

 V-a. **핵심**: 실행 -> 몇 trial 뒤 Stop -> 다음이 모두 참인가?
      1) 진행 중이던 trial 이 **완료된 뒤** 멈춘다(로그로 확인)
      2) Supabase optuna_runs 에 status="stopped" 와 **중단 시점까지의
         실제 완료 수**가 들어간다 (20 배수가 아니라 정확한 수)
      3) 결과 JSON 이 생성되고 best_params 가 들어있다
      4) study sqlite 와 -wal/-shm 파일이 정리된다
      5) 취소 플래그 파일이 지워진다
 V-b. completed 정확도: 중단 시점의 실제 완료 trial 수와 저장된
      n_trials_completed 가 **일치**하는지. (수정 전에는 어긋난다 -
      수정 전/후 값을 같이 보고할 것)
 V-c. queued 상태에서 Stop: 대기열에서 사라지고 즉시 stopped 가 되는지.
      대기열 순번이 밀려 있던 다른 런이 정상적으로 시작되는지.
 V-d. 0 trial 중단: 결과 카드가 NaN 없이 표시되는지.
 V-e. 소유권: 다른 사용자의 run_id 로 취소 시도 -> 403.
      (계정이 하나뿐이면 "코드 리뷰로 확인"이라고 정직하게 보고)
 V-f. 멱등: 이미 stopped 인 런에 Stop 을 다시 눌러도 500 이 안 나는지.
 V-g. 강제 종료 안전장치: WSC_CANCEL_GRACE_SECONDS 를 5 초로 낮추고,
