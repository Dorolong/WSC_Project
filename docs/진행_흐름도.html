02

무엇을 고민했고 왜 그렇게 정했나

기각한 선택지가 고른 것만큼 중요하다. 나중에 "그때 왜 그렇게 했지"로 되돌아오지 않으려면 버린 이유가 남아 있어야 한다.

축 3웹을 어디에 어떻게 올릴까
✕GitHub Pages 프론트 + Supabase 백엔드
정적 호스팅이라 무거운 Python 연산을 못 돌린다
✕Streamlit Cloud에서 Optuna 탐색까지
무료 티어 리소스 한계 + 여러 사용자가 한 프로세스를 공유한다
✓시뮬레이터는 웹, 탐색은 별도 서버로 분리
연산 성격이 다르니 배치도 나눈다
축 3Streamlit을 계속 쓸까
✕Streamlit 유지
다른 HTML 기반 웹과 합칠 예정인데 합칠 방법이 없다
✓HTML + CSS + JS + FastAPI로 재작성
같은 도메인 아래 경로로 나눌 수 있게 된다. 결과적으로 로컬 실행 길도 열렸다
축 4기존 텔레메트리 시스템을 어떻게 쓸까
✕ArrowPoint를 통째로 서버에 올리기
Splunk + TimescaleDB + JVM이 5GB 이상 필요한데 인스턴스가 1GB다
✕원본의 측정항목 정의 재사용
더미값이었다. 우리 명세가 더 정확하고 우선순위 구분까지 있다
✓값 디코딩 규칙과 UDP 프레이밍만 차용
13년간 실전 검증된 부분만 가져오고 나머지는 우리 스택으로
축 4수신 데이터를 어디에 쌓을까
✕서버에 원본 전량 저장
대회 전체 9GB. 무료 500MB는 물론 유료 8GB도 넘는다
✕샘플링 주기를 더 낮춰서 줄이기
언더샘플링은 없던 피크를 만든다(에일리어싱). 정확도를 버리는 방향
✓노트북 로컬에 원본, 서버엔 집계만
아웃백엔 인터넷이 없다. 로컬 SSD엔 9GB가 부담이 아니다
축 1규칙 기반을 언제 비용함수로 바꿀까
✕지금 바로 solver 기반으로 전환
물리 버그와 solver 튜닝 문제가 뒤섞여 디버깅이 불가능해진다
✓물리 building block을 먼저 완성한 뒤 전환
코스팅·제동·내리막 캡은 어느 쪽으로 가든 필요해서 버려지지 않는다
축 1강화학습을 지금 붙일까
✕지금 RL 학습 시작
예보=실제인 환경이라 미래를 아는 정책을 배운다. 실전에 안 옮겨간다
✓DP로 가치함수 먼저 → 예보 오차 도입 → 실측 보정 → 그다음 RL
상태가 1차원이라 지금은 DP가 정확하고 빠르다. RL은 상태가 커진 뒤에 값을 한다
전반설정값을 어떻게 다룰까
✕전역 객체를 잠시 바꿨다가 되돌리기
사용자마다 스레드가 달라 중간에 섞인다. 근본적으로 안전하지 않다
✓설정을 인자로 전달 (cfg → const)
한 사람의 설정 변경이 다른 사람 결과를 바꾸지 않는다
03

겪으면서 알게 된 것

설계보다 실제로 터진 것에서 배운 게 많다. 아래는 같은 종류가 반복된 것들이다.

무엇이 터졌나영향배운 것
야간 시간대 날짜가 안 넘어감993 km경계 조건은 A/B로 재봐야 드러난다
거리 배열이 numpy가 아니라 pandas4.2배 느림성능은 추측하지 말고 프로파일러부터
설정이 전역이라 사용자끼리 섞임2회 발생공유 프로세스에선 전역이 곧 버그
미터와 km를 비교 (신호등)조용히 무동작단위 불일치는 에러 없이 몇 주를 간다
NaN이 표준 JSON에 없는 값배치 전량 손실한 건이 500건을 막는다. 실패 본문을 꼭 남길 것
DB 권한과 행 잠금을 혼동401둘은 다른 장치다. 증상으로 구분된다
문서엔 "정리했다", 실제론 없음재구축 불가문서를 믿되 코드로 교차 확인

가장 값비쌌던 습관 — 검증을 못 한 채로 넘어간 작업들. 파이썬이 없는 환경에서 작성된 코드가 여러 번 머지됐고, 그때마다 다른 컴퓨터에서 대신 돌려보고서야 문제가 드러났다. 텔레메트리 NaN 버그도 그렇게 잡혔다.

그래서 검증 스크립트와 샘플 데이터를 저장소에 함께 두는 것을 원칙으로 삼았다. 이제 python scripts/verify_can_decode.py 한 줄이면 누구든 재현한다.

04

남은 길

순서에 이유가 있다. 앞 단계가 뒤 단계의 전제다.

순서
한국에서
1
코스팅·제동 물리 완성
2
열 모델 추가 (신규)
3
DP 가치함수 → 표 생성
4
시험주행 로그로 계수 보정
5
(선택) 예보오차 · 잔차학습

3번이 왜 필요한가 — 지금은 예보와 실제 날씨가 같아서, 매 스텝 다시 계산하는 MPC의 장점이 드러나지 않는다. 예보에 오차를 넣어야 비로소 "미래를 모르는 상태에서 잘하는 것"을 측정할 수 있고, 그래야 RL도 의미 있는 걸 배운다.

4번이 왜 앞서는가 — 틀린 환경에서 학습하면 틀린 것을 잘하게 될 뿐이다. Regen_eff=0.6, Cd=0.081 같은 값이 아직 카탈로그·이론값이다.

05

실전 구성

한국에서 모델을 완성하고, 호주에서는 노트북 한 대로 오프라인 운용한다.

한국

개발 · 학습
  • 물리 모델 정련 — 코스팅·제동·내리막 캡
  • 비용함수 MPC — DP로 가치함수 산출
  • 파라미터 탐색 — 오라클 서버에서 Optuna
  • 실측 보정 — 시험 주행 로그를 업로드해 상수 교정
  • 결과물: 학습된 모델 파일 + 확정 파라미터
표 파일 →

호주

팀원 노트북 · 오프라인
  • CAN 수신 · 대시보드 — 팀원의 기존 시스템이 담당
  • 우리가 보내는 것: 표 파일 하나
  • 표를 읽어 현재 상태에 맞는 권장 속도 표시
  • 파이썬도, 죽을 프로세스도 없음 — 고장날 여지 최소
  • (선택) 컨트롤스탑에서 상태 전송 → 한국이 재계산

왜 표 하나인가 — 현장에 만든 사람이 없다. 그러면 고장날 여지가 가장 적은 형태가 최우선 기준이 된다. DP로 풀면 결과물이 애초에 표라, "DP로 간다"는 결정이 인계 형태까지 자동으로 해결한다.

표는 정적이 아니다 — 축이 상태(거리·SOC·온도·시간여유)이므로, 날씨가 계획보다 나쁘면 SOC가 낮아지고 표가 다른 속도를 내놓는다. 매 순간 "어떤 선택지를 취할까"에 답하는 정책이다.
