2. CAN 디코딩 스펙 (실측 검증 완료 - 추측하지 말 것)
================================================================
아래는 원본 Java 코드를 읽고 canlog.csv 41,397행으로 대조 검증한
결과다. **이 절의 내용을 바꾸지 말고 그대로 구현할 것.**

[ 2-1. UDP 패킷 구조 ]
원본 UdpPacketDeserializer.java 주석에 명시된 구조:

    +-+----------------+-+-------------------+---------+-------+--------+--------+
    |8| 56 Bus ID      |8| 56 Client ID      | 32 ID   |8 Flags|8 Length|64 Data |
    +-+----------------+-+-------------------+---------+-------+--------+--------+

    바이트 0        : 패딩
    바이트 1~7      : 버스 식별자 (7바이트)
    바이트 8        : 패딩
    바이트 9~15     : 클라이언트 식별자 (7바이트)
    바이트 16부터   : CAN 프레임 반복
        +0 ~ +3 : CAN ID (4바이트)
        +4      : 플래그. bit0 = extended, bit1 = RTR
        +5      : 데이터 길이 n
        +6 ~    : 데이터 n바이트
        다음 프레임 시작 = start + 6 + n

Phase 1 에서는 UDP 를 받지 않지만, Phase 2 가 이 구조를 쓰므로
**파서를 UDP 수신과 분리해 순수 함수로 만들어 둘 것**(bytes -> 프레임
리스트). 그래야 Phase 2 가 수신부만 붙이면 된다.

[ 2-2. 데이터 값 해석 - ★ 가장 중요 ★ ]
CAN 프레임의 8바이트 데이터는 **리틀엔디안 float32 두 개**다.

    seg_one (= 로그의 float[0]) = 바이트 0~3 을 리틀엔디안 float32
    seg_two (= 로그의 float[1]) = 바이트 4~7 을 리틀엔디안 float32

원본 CanPacket.java 의 getDataSegmentOne()/getDataSegmentTwo() 와 동일.

**[함정] canlog.csv 의 data 컬럼은 바이트가 뒤집혀 인쇄돼 있다.**
`0x3F0B17E5457A0000` 를 왼쪽부터 그대로 바이트로 읽으면 쓰레기값이
나온다. 실제 전선 위 바이트는 이 문자열을 **역순**으로 뒤집은 것이다.

    파싱 방법:
        raw = bytes.fromhex(hex_str)[::-1]      # 반드시 뒤집을 것
        seg_one = struct.unpack("<f", raw[0:4])[0]
        seg_two = struct.unpack("<f", raw[4:8])[0]

    검증 예 (canlog.csv 첫 행):
        data = 0x3F0B17E5457A0000
        -> seg_one = 4000.0      (로그의 float[0])
        -> seg_two = 0.543333    (로그의 float[1])

**모든 프레임이 float 쌍인 것은 아니다.** specs 의 명세를 보면
Error_Flags(u8), Mode(u8), Limit_Flags(u16) 같은 정수·비트필드 항목이
있다. 원본에도 getDataSegmentOneInt(), getDataSegmentTwoShortInt() 등이
있다. 따라서 **바이트를 원본 그대로 보관하고, 해석은 신호 정의에
따라 나중에 적용**하는 구조로 만들 것. 저장 시점에 float 으로
단정해 버리면 정수 항목이 망가진다.

[ 2-3. 검증 기준 ]
canlog.csv 를 파싱해 로그의 float[0]/float[1] 컬럼과 대조했을 때
**87.7% 이상 일치**해야 한다. 100% 가 아닌 이유는 위에서 말한
정수·비트필드 프레임을 로그 도구가 억지로 float 으로 찍었기 때문이며,
정상이다. **87% 아래로 나오면 엔디안이나 역순 처리가 틀린 것이다.**
(참고: 잘못된 해석 3가지는 전부 14% 근처에서 멈춘다 - 우연 수준)

3. 신호 정의 (specs/ 의 엑셀을 기계가 읽을 수 있게)
================================================================
 3-1. specs/CAN_수신_데이터_정리본.xlsx 가 유일한 기준이다.
      CAN ID 114개: BMS(HV) 66 확정 / MPPT 21 확정 /
      Motor 13 잠정 / BMS(LV) 14 잠정.

 3-2. **엑셀을 런타임에 직접 읽지 말 것.** 대신 사람이 검토 가능한
      중간 파일 `specs/can_signals.csv` 를 만들어 커밋하고, 코드는
      그것만 읽는다. 최소 컬럼:
        can_id(16진 문자열), group(BMS_HV/BMS_LV/MPPT/MOTOR),
        priority(PRIMARY/DETAIL/SD_ONLY), name,
        seg_one_field, seg_one_type, seg_one_unit,
        seg_two_field, seg_two_type, seg_two_unit,
        status(확정/잠정), note
      type 은 최소 float32 / u8 / u16 / u32 / reserved 를 구분할 것.

 3-3. **엑셀을 프로그램으로 수정하지 말 것.** 이 워크북은 도형·이미지
      (drawings, media)를 포함하고 있어서 openpyxl 로 열었다 저장하면
      **소실된다.** 읽기 전용으로만 열 것.

 3-4. 변환 스크립트(`scripts/can_signals_from_xlsx.py` 등)를 만들어
      커밋할 것. 엑셀이 갱신되면 다시 돌려 CSV 를 재생성한다.
      **자동 변환이 애매한 행은 추측해서 채우지 말고**, 스크립트가
      "확인 필요" 로 표시하고 보고서에 그 목록을 남길 것.

 3-5. Motor 와 BMS(LV) 는 **잠정** 상태다(VCU 미확정). 코드가 이
      상태를 알 수 있어야 하고, 화면에도 잠정임이 드러나야 한다.

 3-6. [알려진 오류 - 고치지 말고 보고만] 엑셀 "시뮬레이션 연계"
      시트 B17/C17 이 "a (가속도, 현재 0 고정) / 매 스텝 갱신되지 않고
      상수로 취급됨" 이라고 돼 있는데 **이미 낡은 정보**다. 실제로는
      Functions/Vehicle_Function.py:45 에서 매 스텝
      `a = (v - prev_v) / dt` 로 계산된다(progress/16, 2026-07-20 완료).
      엑셀 수정은 사용자가 직접 한다.

4. Phase 1 구현 범위
================================================================
[ 4-1. 로그 파서 (신규, 순수 파이썬) ]
 - 위치 제안: `telemetry/` 패키지 신설 (server/ 안에 넣지 말 것 -
   scripts 나 향후 분석 코드도 쓴다)
 - `telemetry/decode.py` : 2절의 규칙 구현.
     * `decode_frame(can_id, data: bytes) -> dict`
     * `parse_udp_packet(payload: bytes) -> list[frame]`  (Phase 2 대비)
     * `parse_canlog_csv(path) -> iterator[frame]`
   **네트워크·DB·웹 의존성이 없어야 한다.** 순수 함수로 둘 것.
 - `telemetry/signals.py` : can_signals.csv 로딩 + can_id -> 신호 정의

[ 4-2. 업로드 API ]
 - `POST /api/telemetry/logs` : 로그 파일 업로드(멀티파트).
   verify_user() 로 인증. 본인 것만.
 - 업로드 즉시 전부 파싱하지 말 것. **파일을 저장하고 run 을 만든 뒤
   백그라운드에서 처리**한다. 기존 시뮬레이션/Optuna 실행이 쓰는
   대기열·진행률·상태 영속화 패턴을 그대로 따를 것
   (server/main.py 의 _try_start_next_sim, _save_runs_state_unlocked 등).
   **새 패턴을 발명하지 말고 있는 것을 재사용할 것.**
 - 파일 크기 상한을 둘 것(환경변수, 기본 50MB 제안). canlog.csv 가
   43,020행 / 약 4MB 다. 1GB 서버임을 잊지 말 것 -
   **전체를 메모리에 올리지 말고 스트리밍 처리**할 것.
 - 레이트 리밋: 업로드는 무거우므로 server/rate_limit.py 의
   enforce_run_creation_rate 계열을 적용할 것(이미 있는 장치를 쓸 것).

[ 4-3. 저장 ]
 - Supabase 에 테이블 2개를 새로 만든다(SQL 은 Codex 가 작성,
   **실행은 사용자가 한다**):
     `telemetry_logs`  : 업로드 단위. user_id, 파일명, 업로드시각,
                         프레임 수, 시간범위, 상태
     `telemetry_frames`: 프레임 단위. log_id, 시각, can_id,
                         raw_data(bytea 또는 hex text), seg_one, seg_two
 - **RLS + GRANT 를 반드시 같이 작성할 것.** optuna_runs 에서 GRANT 가
   빠져 401 이 났던 사고가 있다(progress/48). 두 겹 다 필요하다.
 - 프레임이 수만 건이므로 **배치 insert** 로 넣을 것. 한 건씩 넣으면
   업로드 하나에 수만 번 왕복한다.
 - 원본 파일 자체도 서버에 보관할지 결정하고 보고할 것(디스크가 작다 -
   보관한다면 보존 기간 정책도 같이 제안).

[ 4-4. 화면 ]
 - 기존 통합 웹(server/static/)에 **탭 하나 추가**. nav.js 의 기존
   탭 구조를 따를 것. 새 페이지를 만들지 말 것.
 - 최소 기능:
     * 로그 업로드 + 진행률
     * 내 로그 목록 (시각, 프레임 수, 시간범위, 상태)
     * 로그 하나를 열면 신호별 시계열 차트. 최소한 PRIMARY 신호는
       선택해서 볼 수 있어야 한다
 - 차트는 기존에 쓰는 Plotly 를 재사용할 것(charts.js). 새 차트
   라이브러리를 추가하지 말 것 - CSP 에 출처를 또 열어야 한다.
 - 잠정(Motor/BMS_LV) 신호는 화면에 그 사실이 보이게 할 것.

[ 4-5. Phase 1 에서 하지 않는 것 - 명시적으로 금지 ]
 - UDP 실시간 수신 (Phase 2)
 - 시뮬레이션 가정값 자동 보정 (Regen_eff 등) - 데이터가 쌓인 뒤 별도
   기획. **지금 물리 상수를 건드리지 말 것.**
 - 알림/경보 (원본의 alerts 기능)
 - 원본 대시보드 디자인 이식

5. 검증 (게이트 B)
================================================================
 V-a. **디코더 정확도**: canlog.csv 전체를 파싱해 로그의
      float[0]/float[1] 과 대조. **87.7% 이상 일치**해야 한다.
      일치율과 불일치 샘플 몇 건을 보고서에 넣을 것.
      이 검사를 자동 테스트로 남길 것(회귀 방지).
 V-b. **엔디안 역방향 검사**: 일부러 뒤집기를 빼고 돌렸을 때 일치율이
      15% 아래로 떨어지는지 확인. 떨어지지 않으면 검사가 무의미한
      것이므로 검사 자체를 재검토할 것.
 V-c. **정수 프레임 보존**: raw 바이트가 그대로 저장돼, 나중에 u8/u16
      으로 재해석해도 값이 살아있는지 확인.
 V-d. **업로드 관통**: canlog.csv 를 실제로 업로드 -> 진행률 표시 ->
      완료 -> 목록에 나타남 -> 차트가 그려짐.
 V-e. **메모리**: 업로드 처리 중 파이썬 프로세스 메모리 증가량을 측정.
      1GB 서버 기준으로 과하면 스트리밍 처리를 다시 볼 것.
 V-f. **권한**: 남의 로그 id 로 조회 시 403/404. (계정이 하나뿐이면
      "코드 리뷰로 확인" 이라고 정직하게 보고)
 V-g. **회귀**: 기존 시뮬레이션·Optuna 실행이 안 깨졌는지 확인. 특히
      대기열·상태 영속화를 재사용했다면 반드시 볼 것.
