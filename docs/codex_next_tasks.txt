작업 1 - 회원가입 모달 (사용자 요청, 우선)
================================================================
[ 문제 ]
새 프론트(server/static/)에 **회원가입 기능이 아예 없다.**
index.html 의 #gate 에는 "Sign in" 하나뿐이고, auth.js 에도
signUp 호출이 없다. 원래 Optuna 런처 페이지가 로그인만 갖고 있었고
(계정은 Streamlit 앱에서 만들었다) Phase 1 이 그 구조를 그대로
옮겨왔기 때문이다.
-> **지금 신규 팀원은 새 사이트에서 계정을 만들 수 없다.**
   legacy app.py 로 가입해야만 하는데, app.py 는 없앨 예정이라
   이대로 두면 가입 경로가 사라진다.

[ 요구사항 (사용자 지정) ]
 1-1. 로그인 버튼 **아래**에 회원가입 버튼을 하나 둔다.
 1-2. 누르면 **팝업(모달)** 이 뜬다. 차량 제원 설정과 같은 방식.
 1-3. 모달 입력 항목: **이름, 이메일, 비밀번호** 3개.
 1-4. 가입 버튼을 누르면 Supabase 로 가입 처리.

[ 설계 요구사항 ]
 1-5. 모달은 기존 패턴을 그대로 따를 것. 새로 만들지 말 것:
        index.html:135  <dialog class="modal" id="vehicleConfigDialog">
        index.html:158  <dialog class="modal" id="auxDialog">
      같은 구조로 <dialog class="modal" id="signupDialog"> 를 추가하고,
      열기는 showModal(), 닫기는 close() (vehicle-config.js:218,230 참고).
 1-6. "이름"은 Supabase 의 user_metadata.nickname 으로 저장한다.
      **app.py 의 회원가입과 같은 키를 써야 한다** - 서버가
      닉네임을 그 키로 읽는다(server/main.py 의 create_run 에서
      user_metadata.nickname 사용). 다른 키를 쓰면 대기열에
      이메일이 그대로 노출된다.
      supabase-js 호출 형태:
        client.auth.signUp({
          email, password,
          options: { data: { nickname: <이름> } }
        })
 1-7. 가입 성공 후 처리: Supabase 설정에 따라 이메일 인증이
      필요할 수 있다. **자동 로그인됐다고 가정하지 말 것.**
      app.py 는 "가입 완료. 이메일 인증 후 로그인해주세요."를
      띄우고 로그인 화면에 머무른다 - 같은 흐름으로 맞출 것.
 1-8. 에러 표시는 모달 안에 둘 것. #gateErr 를 재사용하면 모달이
      닫힌 뒤에야 보이므로 안 된다.
 1-9. 빈 값 검사: 이름이 공백이면 가입 진행하지 말 것(app.py 와 동일).
 1-10. 색·간격은 tokens.css 변수만 사용. 색상 리터럴 금지.

[ 검증 조건 ]
 V1-1. 로그인 화면에 회원가입 버튼이 보이고, 누르면 모달이 뜬다.
 V1-2. 모달에 이름/이메일/비밀번호 3개 입력칸이 있다.
 V1-3. **실제로 새 계정을 만들어 본다.** 가입 후:
       - Supabase Auth 대시보드에 사용자가 생겼는지
       - **user_metadata.nickname 에 입력한 이름이 들어갔는지**
         (여기가 틀리면 대기열에 이메일이 노출된다)
 V1-4. 그 계정으로 로그인 -> 시뮬레이션 실행까지 되는지
 V1-5. 이름을 비우고 가입 시도 -> 진행되지 않고 에러가 뜨는지
 V1-6. 이미 있는 이메일로 가입 시도 -> 에러가 **모달 안에** 뜨는지
 V1-7. 모달을 닫았다 다시 열어도 정상 동작하는지
 V1-8. 브라우저 콘솔에 에러·CSP 위반 없음
 V1-9. 색상 리터럴 검사(V1-5d 와 동일한 grep) 통과
 V1-10. app.py 의 회원가입은 **건드리지 않았는지**(금지 2).
        병행 방침상 legacy 쪽은 이미 회원가입이 있으므로 작업 불필요.

[ 완료 판정 ] V1-1 ~ V1-10 전부. 특히 V1-3 의 nickname 확인 필수.
[ 릴리즈 노트 ] 사용자 체감 기능이므로 **양쪽 릴리즈 노트에 항목 추가
  + 버전 올릴 것**: app.py 의 RELEASE_NOTES 와
  server/static/data/release-notes.json (현재 1.1.0).

작업 2 - 서버 재시작 시 실행 상태 소실
================================================================
[ 문제 ]
server/main.py 의 RUNS(dict) 와 QUEUE(list) 가 **메모리 전용**이다.
서버를 재시작하면(배포, 재부팅, 크래시) 진행 중이던 실행 정보가
통째로 사라진다. 증상:
 - 진행률 카드가 사라지고 사용자는 자기 실행이 어떻게 됐는지 모름
 - /api/my-active-run 이 빈 응답을 주므로 복구도 안 됨
 - 대기열에 있던 사람들의 순번이 날아감
 - **자식 프로세스는 살아있을 수 있다**(systemd 가 uvicorn 만
   재시작하므로) -> 서버는 모르는데 탐색은 계속 도는 유령 상태

실제로 2026-08-05 배포 중 이 상황이 관찰됐다. 재시작 직후
/api/sim/runs/{id} 폴링이 404 를 받기 시작했다(로그 07:26:45~46).

완료된 결과는 outputs/study_results/*.json 과 Supabase 에 남으므로
**데이터가 유실되는 건 아니다.** 잃는 것은 "지금 뭐가 돌고 있는지"
라는 실행 상태다.

[ 설계 요구사항 ]
 2-1. **먼저 설계를 제출하고 승인받을 것.** 아래는 방향 제안이며
      더 나은 방법이 있으면 근거와 함께 제시할 것.
 2-2. 상태를 파일에 남기는 방식을 기본으로 검토한다.
      outputs/runs_state.json 같은 단일 파일에 RUNS/QUEUE 를
      직렬화하고, 기동 시 읽어 복원한다.
      - **access_token 을 파일에 쓰지 말 것**(금지 4). 토큰이 필요한
        재개는 포기하고, 복원된 실행은 "조회 전용"으로 두는 것도
        선택지다. 이 판단을 설계에 명시할 것.
      - 쓰기는 상태가 바뀌는 지점에서만(큐 추가/시작/종료).
        폴링마다 쓰지 말 것.
 2-3. **살아있는 자식 프로세스 처리 방침을 정할 것.** 재시작 후
      pid 가 남아있어도 그 프로세스를 다시 감시할 수 있는지,
      아니면 고아로 두고 결과 파일만 볼 것인지. 후자가 단순하다.
 2-4. 복원 실패가 서버 기동을 막으면 안 된다. 파일이 깨졌으면
      로그만 남기고 빈 상태로 시작할 것.
 2-5. SQLite 를 쓰는 방안도 검토 가능하나(이미 optuna_study.db 로
      sqlite 를 쓰고 있음), 이 용도엔 과할 수 있다. 선택 근거를
      설계에 적을 것.

[ 검증 조건 ]
 V2-1. 탐색 또는 시뮬레이션을 시작한 뒤 서버를 재시작한다.
       재시작 후 /api/my-active-run 이 그 실행을 여전히 돌려주는지.
 V2-2. 진행률 카드가 새로고침 후에도 복원되는지.
 V2-3. 대기열에 2건 이상 넣고 재시작 -> 순서가 유지되는지.
 V2-4. 상태 파일을 일부러 깨뜨린 뒤 기동 -> **서버가 죽지 않고**
       빈 상태로 뜨는지, 로그에 경고가 남는지.
 V2-5. 상태 파일에 access_token 이나 비밀번호가 **없는지**
       (파일을 열어 직접 확인하고 보고서에 명시).
 V2-6. 완료된 실행의 결과 조회가 재시작 전후로 동일한지.
 V2-7. 재시작을 반복해도 상태 파일이 무한히 커지지 않는지
       (오래된 항목 정리 방침이 있는지).

[ 완료 판정 ] V2-1 ~ V2-7 전부. 특히 V2-5(토큰 미포함) 필수.
